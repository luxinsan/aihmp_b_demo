# 系统调研与框架校验

## 1. 文档定位

本文用于沉淀系统重构前的业务调研、行业联网调研和顶层功能框架校验，目标是基于真实系统现状与行业依据，重新梳理系统分端、核心业务模块、关键业务对象、跨端流程和权限边界，并校验 `系统功能框架.md` 的定位与结构是否合理。

当前仓库中的前端壳仅作为历史演示材料参考，不能直接代表真实系统功能现状。后续系统功能架构、信息架构、业务模型、权限模型和数据模型应以真实系统调研结果为准。

本文与 `系统功能框架.md` 的关系：

- `系统调研与框架校验.md`：记录调研事实、行业依据、推导逻辑和待确认问题。
- `系统功能框架.md`：沉淀面向系统重构的顶层功能框架和目标态信息架构。
- 本文用于支撑和校验后者，避免顶层框架变成缺少依据的菜单堆叠。

全局表达约束：

- 表述应保持严谨专业、精简干练。
- 优先使用明确结论、结构化条目和业务对象名称。
- 避免口语化描述、重复解释、泛泛形容和未经确认的绝对化判断。
- 对调研事实、行业依据、推导结论、目标态建议和待确认问题必须明确区分。

## 2. 已确认的系统分端

当前系统按使用对象和管理边界初步分为三端。

### 2.1 平台管理端

别名：

- 平台 M 端
- M 端

初步定位：

- 面向平台侧管理人员。
- 当前真实能力非常薄弱，主要只有租户基础信息管理，相当于创建基础租户账号。
- 当前各种配置与管理仍高度依赖人工配置与部署。
- 目标态上，M 端应逐步承担平台级租户、资源、配置、运营和治理能力，但这属于重构规划方向，不是当前真实现状。

待确认问题：

- M 端是否仅平台内部使用，还是也开放给租户管理员。
- M 端未来是否承担租户开通、资源分发、平台内容管理、平台运营和审计职责。
- 当前人工配置与部署中，哪些能力必须在本轮信息架构中产品化。

### 2.2 医护端

别名：

- B 端
- 各个租户的工作站

初步定位：

- 面向医生、护士、健康管理师、医院/机构领导等真实业务用户。
- 承担患者管理、任务处理、方案和内容配置、组织权限管理等主要工作。
- B 端是当前业务管理闭环的主要操作端。

### 2.3 患者端

别名：

- C 端
- 各个租户的用户端
- 小程序

初步定位：

- 面向患者、居民或健康管理服务对象。
- 承担健康任务执行、方案查看、提醒接收、AI 助手交互、个人信息和健康档案查看等能力。
- 真实系统形态为小程序。
- 当前演示前端壳使用 H5 形态可以接受，后续信息架构不应被演示形态限制。

## 3. 行业联网调研与框架校验

本节用于校验当前 `系统功能框架.md` 的顶层结构是否符合数字健康、互联网医疗、慢病管理、健康数据治理和互联互通标准的主流方向。

### 3.1 调研范围

本轮行业联网调研优先覆盖以下方向：

- 政策与监管：全民健康信息化、互联网+医疗健康、互联网诊疗和健康数据安全。
- 数字健康框架：以人为中心、连续服务、可持续数字健康能力。
- 健康管理业务模型：慢病管理、患者自我管理、医护团队协作、远程监测。
- 患者服务与参与：患者端任务执行、提醒、反馈、查询和健康教育。
- 数据互联互通标准：患者、健康档案、CarePlan、Task、Questionnaire 等对象建模。
- AI 医疗健康应用：知识依据、生成追溯、审核、归档和审计边界。

### 3.3 对当前顶层框架的校验结论

当前 `系统功能框架.md` 采用“三端 + 能力分层 + 业务主轴 + 核心对象”的结构，整体合理。

合理性依据：

- **三端划分合理**：M 端承载平台治理，B 端承载医护工作站，C 端承载患者服务，符合多租户健康管理平台的用户分工。
- **能力分层合理**：平台治理层、业务管理层、资源配置层、数据底座层、患者服务层、AI 能力层，能够区分底座能力、业务能力、配置能力和面向患者的服务能力。
- **健康数据中心作为底座合理**：行业政策和数字健康框架均强调数据标准、互联互通、数据治理和安全管控，数据中心不应只是某个端的页面模块。
- **健康管理方案作为核心业务对象合理**：慢病管理和持续健康管理都需要照护计划或管理方案作为组织任务、资源、监测和评估的核心载体。
- **任务闭环作为执行载体合理**：任务把方案落实为患者或医护可执行动作，是连接 B 端管理和 C 端执行的关键对象。
- **AI 能力层作为贯穿能力合理**：AI 助手不应只作为聊天入口，应与患者档案、方案、任务、知识库、归档和审计关联。

### 3.4 当前框架需要增强的点

`系统功能框架.md` V0.1 已具备顶层结构，但要成为重要基准文档，需要继续增强以下内容。以下增强项已作为 V0.2 修订依据：

- 增加行业依据说明，说明为什么采用“三端 + 能力分层 + 业务主轴 + 核心对象”。
- 增加横向治理能力，包括多租户隔离、角色权限、数据权限、操作审计、安全合规、版本管理和发布审核。
- 明确健康数据中心是基础设施，不是一个普通功能模块。
- 明确健康管理方案是业务编排对象，负责组织任务、问卷、文章、知识库、指标、预警和评估。
- 明确知识库既服务方案配置，也服务 AI 生成依据。
- 明确 AI 能力需要有依据追溯、人工审核、归档和审计边界。
- 明确 M 端当前现状与目标态差距，避免把目标态能力误认为当前已有。

补充校准：

- 当前阶段先确定功能颗粒度，不展开常规增删改查等操作级功能点。
- 模块划分不是当前核心任务，应先沉淀功能点基线，再根据业务对象、角色和流程做菜单归类。
- B 端工作台保留，但定义为信息聚合入口，不作为业务主数据模块。
- 健康方案在 B 端本质上是模板管理能力，应归入配置管理下的健康方案模板。
- 健康方案模板匹配患者后生成患者方案实例，患者方案实例主要在患者档案中呈现。
- B 端框架已进一步调整为菜单-页面框架初稿，围绕慢病管理闭环组织。
- 知识库管理独立为一级功能，因为它不只服务方案模板，也服务 AI 生成、报告生成、问答依据和内容推荐。
- 运营管理与数据统计分离：运营管理偏过程推进，数据统计偏结果分析。
- 组织与权限、系统设置分离：前者管理组织、人和权限，后者管理字典、参数、通道、同步和日志。
- B 端工作台当前只保留一级入口，不展开子菜单页面，后续按信息聚合和角色化工作入口单独设计。
- 患者管理当前只保留全部患者、在管患者、患者档案三个稳定页面。
- 患者分组更适合作为患者列表场景中的动作、筛选维度或入组结果，不先作为独立菜单。
- 患者标签若用于筛选和分类，应承载在患者列表/档案场景；若用于标签体系维护，应归入方案与资源管理下的标签管理。
- `配置管理` 更名为 `方案与资源管理`，用于承载健康方案模板、问卷、文章、指标、标签、规则等业务生产资料。
- 数据统计当前只保留一级模块，不展开子项；统计口径应在业务功能定型后再细化。
- B 端框架进一步按慢病健康管理工作流重组，健康管理作为业务母题，不作为普通一级菜单。
- `患者管理` 调整为 `患者中心`，强调其作为健康管理服务对象中心。
- `方案与资源管理` 暂时调整为 `配置中心` 与 `内容与知识`：前者承载方案模板、任务模板、问卷量表、宣教内容、指标规则、分组规则、预警规则、消息模板、评估规则等前置资产和业务规则；后者聚焦知识库及其专业依据管理。
- `风险干预` 独立承载预警事件、风险患者和干预记录，不再作为普通任务列表的附属项。
- `管理评估` 独立承载阶段评估、结营评估、评估报告和 AI 生成报告。
- `服务运营` 替代 `运营管理`，用于表达健康管理服务过程推进，不与数据统计混同。
- AI 不单独作为一级菜单，应嵌入患者中心、配置中心、任务管理、风险干预、管理评估、内容与知识、服务运营等业务场景。
- 当前阶段 B 端功能框架进一步收敛为：工作台、患者管理、任务中心、配置中心、知识管理、组织管理、系统管理。
- 患者管理当前只保留全部患者、在管患者；患者档案暂不作为独立菜单。
- 任务中心暂不展开子项，后续回到健康管理方案体系中统一梳理执行、跟踪、信息采集、宣教、打卡、预警干预等边界。
- 配置中心当前只保留方案模板、问卷量表、宣教内容、管理主题。
- 知识管理聚焦知识库及专业依据管理，区别于配置中心中的业务资产。
- 组织管理与系统管理当前先作为两个一级模块保留，后续再细化角色权限、字典参数、消息通道、数据同步和日志等边界。

关键调研问题：

### 4.2 任务管理

待调研任务类型：

- 随访任务。
- 健康宣教任务。
- 问卷填写任务。
- 指标采集任务。
- 复查提醒。
- 用药提醒。
- 人工处理任务。
- AI 生成待确认任务。
- 异常预警处理任务。
- 干预任务。

关键调研问题：

- 任务是系统自动生成、医护手动创建，还是由健康管理方案模板触发。

- 任务是否区分医护任务和患者任务。
- 任务是否有统一状态流转，例如待处理、处理中、待患者完成、已完成、已逾期、已关闭。
- 任务完成结果是否回写患者档案、方案进度、预警闭环或效果评估。

## 7. 跨端核心业务流程

后续功能架构需要从模块树进一步收敛到业务流程。初步建议重点调研以下主流程。

### 7.1 租户开通流程

初步流程：

```text
平台创建租户
-> 配置租户信息
-> 配置组织 / 人员 / 权限
-> 分配平台资源
-> 初始化 B 端工作站
-> 初始化 C 端入口
-> 租户开始使用
```

待确认：

- 哪些步骤当前已存在。
- 哪些步骤由平台完成，哪些由租户管理员完成。
- 是否存在实施交付流程。

### 7.2 患者建档流程

初步流程：

```text
创建 / 导入 / 同步患者
-> 绑定租户 / 科室 / 团队 / 医护
-> 建立健康档案
-> 补充标签 / 分组
-> 进入健康管理服务
```

待确认：

- 患者数据已确认是多源数据，需进一步按健康数据中心方案细化来源类型、接入方式、患者身份匹配、来源追溯和业务取数规则。
- 多来源数据如何合并。
- 患者身份如何去重。
- C 端患者是否参与建档和补充档案。

### 7.3 健康管理方案流程

初步流程：

```text
配置方案模板
-> 选择患者 / 分组
-> 分配方案
-> 生成患者方案实例
-> 派发任务
-> 患者执行
-> 医护跟进
-> 阶段评估
-> 调整或结营
```

待确认：

- 健康管理方案已确认是系统核心业务对象，也是健康管理的核心手段和方式。
- 方案模板与患者方案实例的数据关系。
- 方案与患者关联后生成可执行任务。
- 问卷、文章、知识库作为资源服务于方案。
- 知识库同时作为 AI 生成结果的重要依据。

### 7.4 任务闭环流程

初步流程：

```text
系统 / 医护 / 方案 创建任务
-> 分配执行人
-> 触达执行人
-> 执行任务
-> 记录结果
-> 逾期 / 异常提醒
-> 回写业务对象
-> 归档
```

待确认：

- 任务是否有统一任务中心。
- 医护任务和患者任务是否统一建模。
- 任务结果回写到哪些对象。

### 7.5 内容资源流程

初步流程：

```text
平台 / 租户 创建资源
-> 审核
-> 发布
-> 被方案 / 任务 / AI 助手引用
-> 统计使用
-> 版本更新
```

待确认：

- 知识库、问卷、文章、方案模板是否共用资源管理机制。
- 是否需要审核与发布。
- 是否需要引用追踪和版本锁定。

### 7.6 AI 辅助流程

初步流程：

```text
获取患者档案 / 任务 / 方案 / 知识库上下文
-> AI 生成建议 / 报告 / 问答 / 任务草稿
-> 医护确认或患者查看
-> 记录结果
-> 回写业务流程
```

待确认：

- AI 在 M 端、B 端、C 端分别承担什么角色。
- AI 生成内容是否需要审核。
- AI 操作是否进入审计。
- AI 结果是否能直接影响任务、方案和患者档案。

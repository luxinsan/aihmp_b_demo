# 健康管理方案体系 V3.0

## 1. 文档目的

本文定位为健康管理方案体系的业务框架说明文档，用于定义系统中健康管理方案的核心概念、内容框架和模块关系，为后续健康管理方案相关功能设计提供统一业务依据。

本文重点回答以下问题：

- 什么是健康管理方案。
- 健康管理方案、方案模板和患者健康计划实例之间的基本关系。
- 一份慢病或长期健康管理方案应包含哪些核心内容。
- 监测数据、打卡、任务、预警干预、阶段评估等能力如何围绕健康管理主题组织。
- 后续系统建设应如何兼顾标准化配置与患者个体化执行。

本文不展开具体页面交互和技术实现。

## 2. 概念定义

健康管理方案体系不应被理解为单一的“计划编辑器”或“任务配置工具”，而应被定义为：围绕特定健康管理主题，将管理目标、监测数据、打卡机制、健康干预任务、预警干预和阶段评估组织起来的一套服务执行框架。

- **健康管理主题**：
  
  - 健康管理主题是方案设计的上层业务分类，用于定义某一类健康问题或管理场景的标准管理框架。
  
  - 健康管理主题决定该类方案通常需要关注哪些指标、设置哪些目标、配置哪些打卡项、设计哪些任务、触发哪些预警干预以及如何做阶段评估。
  
  - 示例：高血压管理；2 型糖尿病管理；体重管理 等

- **健康管理方案模板**：
  
  - 方案模板是围绕健康管理主题配置的一套可复用标准方案。
  
  - 模板本身不直接代表某个患者正在执行的计划。
  
  - 模板用于提高建方案效率，适合沉淀机构、科室或服务团队的标准管理路径。
  
  - 例如“高血压 90 天管理模板”“体重管理 28 天干预模板”“糖尿病基础管理模板”等。

- **患者健康计划实例**：
  
  - 患者健康计划实例是将方案模板应用到某个患者后形成的个人健康管理计划，也可以由医护人员直接为患者创建。
  
  - 模板负责标准化，实例负责个体化执行。
  
  - 实例可以来源于模板，但生成后应与模板解耦：
    
    - 修改患者实例，不影响模板。
    
    - 修改模板，不影响已生成实例。
    
    - 实例保留创建时的模板快照和来源信息，用于追溯。
    
    - 实例允许根据患者情况做个性化调整。

- **方案文档：**
  
  - 在部分业务场景中，“健康管理方案”也可能指一份正式交付给客户或患者的文档，例如年度健康管理建议书、90 天健康管理方案建议等。
  
  - 这类内容更适合称为“方案文档”。方案文档偏向分析、建议和交付表达，而系统中的健康计划实例偏向执行和跟踪。

## 3. 健康管理方案的内容框架

结合慢病管理、团队照护、自我管理和国内基本公共卫生服务规范中的常见实践，一份完整的健康管理方案建议包含以下核心内容。

### 3.1 管理主题

- 管理主题回答“这份方案主要解决什么健康问题”。

- 管理主题是方案配置的业务入口。主题确定后，系统可以带出该主题下常用的目标、监测数据、打卡动作、干预任务、预警干预和阶段评估方式。

- 不同主题可以共享同一套方案框架，但具体指标、任务、预警和评估内容应随主题变化。

- 示例：控制血压；改善血糖；降低体重和腰围；改善血脂等。

### 3.2 适用对象

- 适用对象回答“这份方案适合谁”。

- 适用对象可转化为方案匹配条件，用于基于患者全面健康数据进行方案推荐、筛选和适配判断。

- 匹配条件可包括疾病诊断、风险等级、关键指标、年龄范围、生活方式、用药情况、既往病史、服务场景等。

- 方案匹配结果可用于辅助医护选择模板，但不应直接替代医护判断。系统可以给出推荐原因、命中条件和需人工确认的风险点。

### 3.3 基线评估

- 基线评估回答“患者当前处于什么状态”。

- 基线评估是制定目标、配置监测数据、设置打卡机制、触发预警干预和后续阶段评估的依据。

- 基线评估应基于当前可获得的患者数据自动抽取，重点覆盖关键指标、既往病史、当前风险、生活方式和依从性基础。

### 3.4 管理目标

- 管理目标回答“这轮管理要达到什么结果”。

- 健康管理目标不是单纯展示字段，而应成为后续监测数据、打卡机制、健康干预任务、预警干预和阶段评估的依据。

- 目标应尽量可量化、可追踪、可复盘，并能关联到具体监测数据或执行动作。无法追踪和评估的目标，不适合作为方案核心目标。

- 目标建议分为 2 类：

| 目标类型 | 目标方向   | 目标示例         | 目标表达方式 |
| ---- | ------ | ------------ | ------ |
| 指标目标 | 血压     | 血压控制在目标范围    | 区间目标   |
| 指标目标 | 血糖     | 空腹血糖达到目标区间   | 区间目标   |
| 指标目标 | 糖化血红蛋白 | HbA1c 降至目标水平 | 上限目标   |
| 指标目标 | 体重     | 体重下降一定比例     | 变化幅度目标 |
| 指标目标 | 腰围     | 腰围下降         | 变化趋势目标 |
| 指标目标 | 血脂     | LDL-C 达标     | 达标目标   |
| 行为目标 | 运动     | 每周完成指定次数运动   | 频次目标   |
| 行为目标 | 饮食     | 每日记录饮食       | 记录目标   |
| 行为目标 | 自测     | 按要求测量血压或血糖   | 执行目标   |
| 行为目标 | 用药     | 规律服药         | 依从性目标  |
| 行为目标 | 饮食控制   | 减少高盐、高糖、高脂饮食 | 行为改善目标 |
| 行为目标 | 睡眠     | 改善睡眠时间       | 变化趋势目标 |

### 3.5 监测数据

- 监测数据是健康管理方案需要持续关注、引用和评估的数据对象，本身不是执行动作。

- 监测数据用于支撑目标配置、预警干预、趋势分析和阶段评估。行为数据、症状数据和过程数据也属于记录结果，不等同于打卡动作本身。

- 系统应建立健康数据条目库，用于统一管理可被方案引用的数据条目。数据条目可与健康管理主题建立关联；当方案主题确定后，系统自动带出推荐监测数据，供方案模板配置和患者计划实例个体化调整。

| 条目类型 | 示例                      | 主要用途           |
| ---- | ----------------------- | -------------- |
| 指标数据 | 血压、血糖、体重、腰围、HbA1c、LDL-C | 目标配置、预警干预、趋势评估 |
| 行为数据 | 饮食、运动、睡眠、用药、饮水          | 依从性判断、行为干预     |
| 症状数据 | 胸闷、头晕、心悸、乏力             | 异常识别、医护跟进      |
| 过程数据 | 问卷完成、复查完成、随访反馈          | 服务闭环、阶段评估      |

```text
健康数据条目库
-> 主题推荐条目
-> 方案模板启用与配置
-> 患者计划实例复制与个体化调整
-> 支持预警干预、阶段评估和报告生成
```

### 3.6 打卡机制

- 打卡是患者侧用于执行、确认、反馈和形成记忆点的轻量动作。

- 打卡可以用于采集监测数据，也可以用于确认行为执行、反馈任务完成、强化习惯养成和记录患者参与情况。

- 打卡是形成记录的动作入口，不等同于监测数据，也不等同于健康干预任务。一次打卡可以产生数据记录，也可以反馈某项任务的完成情况。

| 打卡类型    | 示例               | 主要作用   |
| ------- | ---------------- | ------ |
| 数据型打卡   | 血压打卡、血糖打卡、体重打卡   | 采集具体数据 |
| 行为型打卡   | 运动打卡、饮食控制打卡、喝水打卡 | 记录行为执行 |
| 习惯型打卡   | 早睡打卡、每日步行打卡      | 强化持续参与 |
| 任务反馈型打卡 | 已阅读宣教、已完成问卷、已复查  | 确认任务完成 |
| 症状反馈型打卡 | 今日无不适、头晕反馈、胸闷反馈  | 反馈主观状态 |

行为型打卡形成的结果可沉淀为行为数据，用于后续依从性判断、行为干预和阶段评估。

```text
监测数据
-> 可通过打卡采集

健康干预任务
-> 可通过打卡确认或反馈

打卡机制
-> 形成患者执行记录、习惯反馈和参与感
```

### 3.7 健康干预任务

- 健康干预任务是方案为推动目标达成或处理管理过程问题而安排的执行事项。

- 任务可以面向患者、医护或系统，覆盖宣教、用药、运动、饮食、复查、随访、预警处置和方案调整等动作。

- 健康干预任务强调“要完成什么事”，打卡强调“如何记录或反馈完成情况”。部分任务可以通过打卡反馈，部分任务需要医护处理或系统触发。

| 任务类型   | 执行人     | 示例                  | 与打卡关系              |
| ------ | ------- | ------------------- | ------------------ |
| 患者干预任务 | 患者      | 阅读宣教、服药提醒、运动计划、饮食控制 | 可通过打卡反馈完成情况        |
| 复查任务   | 患者 / 医护 | 检验检查、门诊复诊、上传报告      | 可通过任务反馈型打卡确认       |
| 随访任务   | 医护 / 患者 | 电话随访、线上问卷随访         | 可形成随访记录            |
| 预警处置任务 | 医护      | 审核异常、处理预警、判断转诊      | 通常由监测数据或打卡异常触发     |
| 方案调整任务 | 医护      | 调整目标、任务、随访频率        | 基于监测数据、打卡记录和阶段评估触发 |

### 3.8 预警干预

- 预警是健康管理闭环中的关键机制，用于识别异常状态，并连接后续处理动作。

- 预警不应只是页面提示，而应能触发明确的处理动作，例如提醒患者、通知医护、生成随访任务、建议复诊或升级干预。

- 常见预警类型包括指标异常、症状异常、依从性异常和趋势异常，例如血压或血糖超出阈值、出现胸闷头晕等症状、连续未打卡或任务逾期、指标长期未达标或波动异常等。

- 预警干预应包含：

```text
预警干预
├─ 触发条件
├─ 风险等级
├─ 提醒对象
├─ 处理动作
├─ 是否生成任务
├─ 是否需要医护确认
├─ 是否进入阶段评估
└─ 是否需要记录处理结果
```

### 3.9 阶段评估

阶段评估回答“这一阶段管理效果如何，下一步怎么办”，可按 7 天、14 天、28 天、90 天或年度周期进行。评估重点包括目标达成、指标趋势、打卡与任务完成、随访完成、预警发生与处理、患者反馈和医护评价。评估结果用于判断是否需要调整目标或计划、进入下一阶段、结营或转诊，并可形成阶段总结、健康管理报告、医护建议和下一阶段计划。

## 4. 总结

健康管理方案体系的核心不是“配置一份方案”，而是建立一套可持续运行的服务闭环。

一份成熟的健康管理方案应围绕健康管理主题，标准化组织以下内容：

```text
管理主题
-> 适用对象
-> 基线评估
-> 管理目标
-> 监测数据
-> 打卡机制
-> 健康干预任务
-> 预警干预
-> 阶段评估
```

系统建设上，应坚持：

- 主题标准化。
- 目标可量化。
- 数据可追踪。
- 动作可执行。
- 异常可处理。
- 结果可评估。
- 历史可追溯。





## 5. 行业依据与框架合理性说明

当前健康管理方案内容框架并不是单纯的功能清单，而是围绕慢病和长期健康管理形成的一套服务闭环。

从行业实践看，慢病管理通常不是一次性诊疗行为，而是围绕特定人群持续开展状态识别、目标设定、数据监测、自我管理、干预执行、异常处理和阶段复盘。当前框架能够覆盖这一完整过程。

### 5.1 行业依据

以下行业依据可作为当前内容框架的外部支撑。它们共同指向一个基本判断：健康管理方案应围绕目标人群、基线状态、管理目标、持续监测、患者参与、干预执行、异常处理和阶段复盘形成闭环。

| 行业依据 | 主要来源 | 核心关注点 | 当前框架承接 |
| --- | --- | --- | --- |
| 慢病管理模型 | [CDC - The Chronic Care Model and Diabetes Management in US Primary Care Settings](https://www.cdc.gov/pcd/issues/2013/12_0180.htm) | 自我管理支持、服务流程设计、决策支持、临床信息系统 | 打卡机制、健康干预任务、预警干预、监测数据、阶段评估 |
| 数字健康干预实践 | [WHO - Classification of digital interventions, services and applications in health, 2nd edition](https://www.who.int/publications/i/item/9789240081949) | 用统一语言描述数字健康技术在健康服务中的用途，覆盖个人、服务提供者、健康系统和数据服务等场景 | 监测数据、打卡机制、健康干预任务、预警干预 |
| 行为改变与自我管理实践 | [NICE NG183 - Behaviour change: digital and mobile health interventions](https://www.nice.org.uk/guidance/ng183) | 目标设定、反馈与监测、行为支持、用户能力、动机、健康素养和可及性 | 管理目标、打卡机制、监测数据、健康干预任务、阶段评估 |
| 国内公共卫生慢病管理实践 | [国家基本公共卫生服务规范（第三版）PDF](https://www.nhc.gov.cn/ewebeditor/uploadfile/2017/04/20170417104506514.pdf) | 服务对象、筛查、随访评估、指标测量、症状询问、生活方式、用药情况、分类干预、转诊和下一步安排 | 适用对象、基线评估、监测数据、健康干预任务、预警干预、阶段评估 |
| 糖尿病慢病管理标准 | [American Diabetes Association - Standards of Care in Diabetes](https://professional.diabetes.org/standards-of-care) | 诊断、目标、血糖监测、生活方式管理、药物治疗、并发症风险、个体化管理和持续评估 | 管理目标、监测数据、健康干预任务、阶段评估 |

### 5.2 框架合理性判断

基于以上行业实践，当前框架是合理的。它既覆盖了慢病管理的基本服务过程，也适配数字健康产品所需的配置化能力。

它的核心价值在于把健康管理方案拆成边界清晰的模块：

- 管理主题：定义管理场景。
- 适用对象：定义方案适合谁。
- 基线评估：定义患者当前状态。
- 管理目标：定义要达到什么结果。
- 监测数据：定义需要持续关注的数据对象。
- 打卡机制：定义患者侧记录和反馈动作。
- 健康干预任务：定义需要完成的管理事项。
- 预警干预：定义异常识别和后续处理。
- 阶段评估：定义阶段复盘和下一步判断。

因此，当前框架不应被理解为字段堆砌，而应被理解为一套围绕健康管理主题组织的服务闭环。

### 5.3 后续设计边界

后续产品设计中，需要重点守住以下边界：

- 监测数据是数据对象，不是执行动作。
- 打卡机制是患者侧动作入口，不等同于监测数据或健康干预任务。
- 健康干预任务强调要完成的事项，可以面向患者、医护或系统。
- 预警干预需要同时包含异常识别和后续处理动作。
- 阶段评估用于判断阶段效果和下一步安排，不只是结果展示。

整体来看，当前框架适合作为健康管理方案的标准内容框架，用于指导后续方案模板、患者健康计划实例、打卡、任务、预警干预和阶段评估等能力建设。

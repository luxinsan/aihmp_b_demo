## 2. 已确认系统定位

AI HMP 是面向医院或机构租户的健康管理系统。

系统目标不是单点患者档案、任务、内容或 AI 聊天工具，而是：

```text
以健康数据中心为底座
以健康管理方案为核心组织方式
以任务执行为服务闭环
以知识库和 AI 助手为智能增强能力
的多租户健康管理平台
```

本次排查应围绕健康管理闭环，而不是仅按页面菜单排查。

## 3. 已确认分端与用户

| 端 | 当前理解 | 主要用户 | 备注 |
| --- | --- | --- | --- |
| M 端 / 平台管理端 | 平台治理端 | 平台管理、实施、运营人员 | 当前真实能力很弱，主要只有租户基础信息管理。当前排查归入“平台底座备忘”，默认不主动展开。 |
| B 端 / 医护端 / 医护工作站 | 租户侧业务管理端 | 医生、护士、健康管理师、医院或机构领导 | 当前业务管理闭环的主要操作端。 |
| C 端 / 患者端 / 小程序 | 被服务者端 | 患者、居民、健康管理服务对象 | 真实形态为小程序；演示 H5 不应限制目标信息架构。 |

当前用户提出本次重点按 B 端、C 端排查，因此后续将 M 端问题归入“平台底座备忘”。除非用户特别提到，或 B/C 端流程明显依赖 M 端能力，否则不展开 M 端专项排查。

## 4. 已确认核心业务主轴

系统目标态主轴：

```text
租户开通
-> 组织与人员配置
-> 患者建档
-> 多源健康数据汇聚
-> 健康管理方案制定 / 分配
-> 生成任务
-> 患者执行 / 医护跟进
-> 预警与干预
-> 阶段评估 / 结营评估
-> AI 辅助查询 / 生成 / 执行 / 归档
```

患者健康管理主轴：

```text
患者建档
-> 健康数据汇聚
-> 健康评估
-> 制定 / 分配健康管理方案
-> 生成任务
-> 患者执行任务
-> 医护跟进
-> 数据回写
-> 预警 / 干预
-> 阶段评估
```

本次应修清单排查时，已不需要再确认“是否应按健康管理闭环组织”，该方向已明确。

## 6. B 端已知功能框架

当前收敛后的 B 端框架：

```text
B 端 / 医护工作站
- 工作台
- 患者管理
  - 全部患者
  - 在管患者
- 任务中心
- 配置中心
  - 方案模板
  - 问卷量表
  - 宣教内容
  - 管理主题
- 知识管理
- 组织管理
- 系统管理
```

已明确边界：

- 工作台是信息聚合入口，不是业务主数据模块。
- 健康管理是业务母题，不作为普通一级菜单。
- 患者分组更适合作为患者列表动作、筛选维度或入组结果，不先作为独立菜单。
- 患者档案暂不作为患者管理下的独立菜单，后续结合患者详情页和患者方案实例呈现。
- 方案模板匹配患者后生成患者方案实例。
- AI 不单独作为 B 端一级菜单，应嵌入患者管理、任务中心、配置中心、知识管理等业务场景。

## 8. 健康数据中心已知规则

资料来源：`docs/product-planning/health-data-center-product-solutions.md`。

当前真实状态：

- 当前系统还没有已成型的健康数据中心。
- 健康数据中心已经在建设中。
- 健康数据中心是核心底座能力，建成后预期将大力支撑信息采集、患者档案、方案匹配、预警、阶段评估、报告生成和 AI 助手等业务功能。

产品定位：

- 健康数据中心用于统一接收、保存、加工、标准化和服务患者相关健康数据。
- 凡是系统内需要读取、写入、分析或引用健康数据的场景，原则上都应通过健康数据中心形成统一数据口径。

核心目标：

- 将多来源、异构、非标准、非结构化或半结构化健康数据，保存为可查询、可追溯、可治理、可被业务复用的数据。
- 支持建档、评估、制定方案、随访、报告生成、阶段复盘和 AI 辅助等环节复用同一批健康数据。
- 构建从数据进入、原始保留、加工保存、业务使用到追溯审计的稳定链路。

建设原则：

- 原始资料必须保存，支撑复核、追溯、重加工和审计。
- 按需保存健康数据，不追求全量结构化。
- 多来源数据并存，不由数据中心判断业务场景采用哪条数据。
- 数据标准、处理规则、外部对接方式需要可扩展。

核心能力模块：

| 模块 | 定位 |
| --- | --- |
| 数据接入 | 统一定义健康数据如何进入、记录来源和跟踪接入过程。 |
| 原始数据管理 | 保留原始资料和来源依据，支撑回看、复核、追溯和重加工。 |
| 数据处理 | 将非结构化数据转为解析结果，并完成标准匹配与落表判断。 |
| 标准数据体系 | 定义健康数据在系统中的统一表达口径。 |
| 数据服务 | 作为业务统一数据出口，提供查询、场景化组装、分层返回、溯源随行和上下文供给。 |
| 安全管控 | 记录健康数据被查询、引用、修正、导出、共享等过程，支撑审计。 |

已知关键边界：

- 结构化数据直接走来源引用和按需落表，不进入 AI 解析链路。
- 非结构化数据先保存原始资料，再进入处理层。
- 只有通过按需落表判断的数据，才保存为可复用健康数据。
- 未通过落表的数据仍需保留解析结果或来源引用。
- 业务模块不应绕过数据服务直接取数。
- 业务结论、风险判断和展示优先级由具体业务场景决定，不由数据中心统一判断。

已知数据来源：

- 外部信息系统：基础档案、病历档案、检验检查报告、体检报告、处方等。
- 系统内部病历资料：图片、PDF 等前台上传资料。
- 物联设备：血压、血糖、体重、体脂、运动、睡眠等。
- 系统内其他业务数据：问卷填写、外呼转写、打卡记录、任务执行结果等。

已知待决策事项：

- [P0] 数据归属模型。
- [P0] 外部数据所属患者确认策略。
- [P0] 第一批标准数据项范围。
- [P1] 外部数据排重、合并和重复拉取处理。
- [P1] 原始资料重加工后的结果更新策略。
- [P1] 处理失败、未匹配、低置信度数据的提示和处理方式。
- [P1] 单位标准化和单位换算启用规则。
- [P1] 患者档案、健康报告、方案生成、风险预警、阶段评估等主要业务场景取数口径。
- [P1] 历史报告、方案、预警、评估引用健康数据后是否形成引用快照。
- [P1] 租户隔离、跨租户授权访问和患者授权原则。

## 9. 健康管理方案已知规则

健康管理方案体系的标准内容框架：

```text
管理主题
-> 适用对象
-> 基线评估
-> 管理目标
-> 监测数据
-> 打卡机制
-> 健康干预任务
-> 预警干预
-> 阶段评估
```

关键已知规则：

- 健康管理方案是系统核心业务对象。
- 健康管理主题是方案设计的上层业务分类。
- 方案模板负责标准化，患者健康计划实例负责个体化执行。
- 患者健康计划实例生成后应与模板解耦。
- 修改患者实例不影响模板；修改模板不影响已生成实例。
- 实例需要保留创建时的模板快照和来源信息。
- 适用对象可转化为方案匹配条件，但不应直接替代医护判断。
- 管理目标应可量化、可追踪、可复盘。
- 监测数据是数据对象，不是执行动作。
- 打卡是患者侧记录和反馈动作，不等同于监测数据或健康干预任务。
- 健康干预任务强调“要完成什么事”，可以面向患者、医护或系统。
- 预警不应只是页面提示，应触发明确处理动作。
- 阶段评估用于判断阶段效果和下一步安排，不只是结果展示。

## 10. 信息采集引擎已知规则

健康信息采集引擎不是普通问卷管理，而是底层信息采集能力。

已确认核心规则：

- 问卷是底层采集工具。
- 量表是问卷在医学或健康专业场景下的专业化形态。
- 随访表单是问卷在随访任务中的业务应用。
- 健康自测是问卷在患者自测场景中的业务应用。
- 答卷记录是用户或医护完成一次问卷后的原始回答结果。
- 题目不应只是文案和控件，应具备题目含义、标准数据项、答案类型、单位、时间语义和落表能力。
- 题目绑定标准数据项，回答“这道题采集的是什么数据”。
- 业务场景决定本次填写是否实际落表，以及以什么来源和业务语义落表。
- 原始答卷需要长期保存。
- 已提交问卷支持修改，每次修改形成新的答卷版本。
- 修改影响已绑定数据项时，新版本应重新触发落表，旧版本来源健康数据标记为更正或失效。
- 落表失败不应阻断答卷提交。
- 预填写应从健康数据中心读取，并按题目时间语义过滤，不应简单读取最近一条。

本期需要建设：

- 平台题库。
- 题目语义。
- 数据项绑定。
- 答案类型和单位约束。
- 问卷题目快照。
- 结构化答卷结果。
- 基于健康数据中心的预填写。
- 绑定数据项后的落表处理。
- 落表状态记录。
- 原始答卷长期保存。
- 答卷修改和历史版本。
- 轻量跳题和显隐。
- AI 辅助题目含义识别、相似题推荐和标准数据项推荐。

## 11. 已知推进优先级

来自升级排期建议的优先级基线。

### P0 必做

- 患者档案数据中心 MVP。
- 外部数据保存、清洗、有限落表。
- 统一档案数据接口。
- 指标库和主题指标关系。
- 问卷 / 量表题目与指标映射。
- 健康管理主题和方案结构升级。
- 打卡功能底层逻辑重构。
- 规则预警和干预任务闭环。
- 阶段或结营效果评估 MVP。
- C 端建档、采集、任务执行主链路。

### P1 强建议

- 标签分组和统一分组模块。
- 报告生成与 B 端同步展示。
- C 端 AI 助手统一入口。
- AI 助手查询档案、报告、任务、进度。
- 租户级、团队级配置开关整合。
- 企微触达链路。

### P2 后置增强

- 智能分组。
- 信息采集预填写。
- 基于知识库的 AI 方案生成。
- AI 预警策略生成。
- 语音交互全面升级。
- 个性化生活方式干预任务。
- 依从性总结分析。
- 阶段或结营管理效果智能分析。

## 12. 已知主要风险

| 风险 | 已知建议 |
| --- | --- |
| 所有模块同时开工但底层口径不一致 | 先冻结患者唯一身份、多租户归属、档案数据分层、来源追踪、指标编码、任务/打卡/预警/干预/评估状态模型。 |
| AI 场景效果依赖数据质量和知识库成熟度 | 每个 AI 场景都要可人工编辑、可追溯数据来源、可按租户关闭、生成结果可二次确认。 |
| C 端入口过多导致体验分散 | 用 AI 助手和任务中心收敛入口，不直接堆页面。 |
| 语音、强智能分组、模型全量扫描不确定性高 | 不建议放入一期硬交付，应作为后置增强包。 |

## 13. 后续不要重复追问的事项

以下内容已在系统重建文档中明确，后续访谈不应再作为开放性问题重复询问，只在发现现状与文档冲突时确认：

- 系统核心定位是健康管理闭环平台。
- B 端主要用户包括医生、护士、健康管理师、医院或机构领导。
- C 端真实形态是小程序，服务患者、居民或健康管理服务对象。
- 租户核心锚点是医院或机构。
- 健康管理方案是核心业务对象。
- 方案模板关联患者后生成患者健康计划实例或患者方案实例。
- 问卷、文章、知识库是服务健康管理方案的资源。
- 知识库也是 AI 生成结果的重要依据。
- C 端 AI 助手是围绕健康管理的全场景助手。
- 健康数据中心是底座能力，不是普通页面模块。
- 当前系统还没有已成型的健康数据中心，但该能力已经在建设中。
- 信息采集引擎不是普通问卷工具。
- 任务是连接 B 端管理和 C 端执行的关键对象。
- 预警必须连接处理动作和闭环记录。

## 14. 后续仍需确认的问题

这些问题是已有文档明确标注的待确认事项，后续排查可优先围绕它们收敛：

- 当前真实系统中哪些目标态能力已经存在，哪些只是规划。
- M 端人工配置与部署中，哪些必须产品化。该项仅作为平台底座备忘，除非特别提到，否则不主动展开。
- 医护、护士、健康管理师、机构领导的具体权限、数据范围和高频任务。
- 患者是否可以属于多个租户、科室、团队或医生。
- 多源患者身份如何匹配、合并、去重和追溯。
- 健康管理方案模板与患者实例的具体数据关系和版本策略。
- 任务是否需要统一建模，医护任务和患者任务如何区分。
- 任务状态流转、逾期、关闭、回写和归档规则。

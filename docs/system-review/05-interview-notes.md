## 2026-05-21 初始共识

### 排查方式

- 当前代码结构只能反映系统功能的一小部分，因此本次排查以业务访谈和流程走查为主。
- 系统主要分为 B 端和 C 端。
- B 端、C 端都包含业务功能和底座功能。
- 排查逻辑采用：先按业务闭环走，再按端拆责任，最后按底座能力归因。

## 后续访谈记录

### 轮次 1：系统边界确认

- B 端面向医护、健康管理师等参与健康管理的人员，以及机构管理者。这类角色在已有文档中多次出现。
- C 端主要面向群众，即常规需要做健康管理的人群、被服务者。不同业务场景下称呼有差别，但当前排查不需要先细分命名。
- 当前系统最核心的业务闭环是：从筛选识别到健康管理闭环。
- B 端当前最重要的业务功能包括：智能分组、健康管理方案、健康任务执行、预警。
- C 端当前最重要的业务功能包括：健康任务执行、数据监测、AI 助手、信息采集、预警。

### 本轮初步归纳

- 排查主线可先按“筛选识别 -> 智能分组 -> 健康管理方案 -> 健康任务执行 -> 数据监测 -> 预警 -> 闭环处理”展开。
- B 端重点看服务组织、方案制定、任务跟进、预警处理和管理质控。
- C 端重点看被服务者是否能理解并完成任务、查看数据、接收预警、获得 AI 辅助和完成信息采集。
- 下一轮建议先确认“筛选识别”这个起点，因为它决定后续分组、方案和任务从哪里来。

### 轮次 2：健康数据中心

- 当前系统还没有已成型的健康数据中心，但该能力已经在建设中。
- 健康数据中心是核心底座能力，具体产品方案参考 `docs/product-planning/health-data-center-product-solutions.md`。
- 用户确认：如果数据中心建成，预期能大力支持各种业务功能。
- 本轮后续问题不再重复追问，改为直接依据健康数据中心产品方案提炼。

### 本轮初步归纳

- 健康数据中心应作为跨端底座排查，不作为 B 端或 C 端单点页面问题。
- 当前应修清单需要记录“能力建设中”这一状态，并追踪其对信息采集、患者档案、方案、任务、预警、报告、阶段评估和 AI 助手的依赖。
- P0 级待收敛事项包括数据归属模型、外部数据患者匹配策略、第一批标准数据项范围。
- P1 级待收敛事项包括主要业务场景取数口径、引用快照、来源追溯和安全管控规则。

### 轮次 3：业务流程起点校准

- 当前系统没有“目标人群”概念，统一称为患者；在特殊预警等场景下可根据业务语境转换称呼。
- 患者主要有两种进入方式：通过 API 向院内系统拉取患者数据；通过 C 端注册。
- 两种方式进入的患者都会进入系统统一患者池。
- 当前没有明确“筛选识别”流程，这个环节先挂起。
- 筛选结果进入哪里、最大问题是什么等问题暂不展开。

### 本轮初步归纳

- 后续主流程起点调整为“患者进入统一患者池”，而不是“筛选识别目标人群”。
- 筛选识别业务定位不明确，暂不进入应修清单，也不作为下一步排查主线。
- 下一步应继续排查“患者进入患者池之后如何建档、绑定、去重、归属确认，以及 B/C 两端如何感知”。

### 轮次 4：患者池、建档与档案匹配

- 院内 API 拉取来的患者信息是完整的。这里的“完整”指能够满足业务需求；不同租户对数据的要求不同，无法用同一个标准评价数据是否完整。
- C 端注册进入的是用户，用户需要建档后才有档案概念。
- 档案记录统一管理。无论从哪个方式获得患者档案，都会先查库是否已有对应档案；无则新增，有则匹配。匹配校验规则参考健康数据中心文档。
- 患者会有机构归属，即租户，同时会带科室信息。
- 分配团队是后续动作，需要重点梳理。
- 当前建档最大的问题是流程混乱，多次迭代后已经不可维护，需要重新梳理。

### 本轮初步归纳

- 数据是否完整不应使用全局统一标准判断，而应按租户和业务场景判断是否满足使用要求。
- 需要区分 C 端用户、患者、患者档案三个对象。
- 患者档案应作为统一管理对象，院内 API 拉取和 C 端注册最终都应走档案查重、匹配或新增逻辑。
- 当前建档流程不可维护，应进入系统应修清单，作为患者进入健康管理闭环的 P0 入口问题。
- 下一步建议继续排查“团队分配 / 在管关系”，因为用户明确这是后续动作且需要重点梳理。

### 轮次 5：排查方式重塑

- 线性流程和 B/C 二元结构不足以承载建档这类立体命题。
- 后续改为按核心业务命题做专题排查。
- 每个专题区分两条线：业务背景知识、系统构建。
- 当前先从“患者管理”大模块开始。

### 本轮初步归纳

- 患者管理不是单一页面，而是横跨患者池、C 端注册、院内 API 拉取、患者档案、租户 / 科室归属、团队分配、在管关系、健康数据中心和后续方案 / 任务 / 预警的核心专题。
- 主文档已新增“患者管理专题”，后续围绕该专题继续补充业务背景知识和系统构建。

### 轮次 6：患者管理对象关系

- 患者和患者档案是一对一关系。
- 一个患者对应一个自然人。
- 一个 C 端用户可关联多个患者档案，用于家庭式管理。
- “用户”是系统语境用词。
- 院内 API 拉取来的患者，即使没有 C 端用户，也可以被 B 端管理。
- 患者进入系统并具备租户、科室归属后，不会自动成为在管患者；是否要管是另一个业务层面的动作。

### 本轮初步归纳

- 患者管理专题中需要明确三组关系：C 端用户与多个患者档案、患者与患者档案一对一、患者池与在管关系分离。
- “患者进入患者池”只表示对象进入系统并具备基础归属，不代表已纳入健康管理服务。
- 后续应重点梳理“团队分配 / 在管关系”，明确患者从患者池进入在管状态的业务动作、规则和系统承载。

### 轮次 7：切换到组织管理专题

- 当前应先从组织管理模块梳理，而不是继续直接追团队分配。

### 本轮初步归纳

- 组织管理是患者管理、团队分配、在管关系、任务执行、预警处理和数据权限的前置底座。
- 主文档已新增“组织管理专题”，同样区分业务背景知识和系统构建两条线。
- 患者管理专题中的团队分配 / 在管关系已标注为依赖组织管理。

### 轮次 10：组织管理 - 机构管理

- 机构在实际中可为医院、医疗机构、健康管理机构等，在系统中对齐租户层级。
- 院区是租户层级下的组织形态，具体层级为租户 -> 院区 -> 科室。
- 实际业务中不一定会有院区和科室，有些机构不需要这些组织层级，需要兼容。
- 一个机构即租户，患者、人员、数据都归属这个租户。
- 一个租户对应一个小程序，即一个 C 端入口。
- 组织管理最大的问题是系统难以兼容实际业务的复杂情况，需要专门展开。

### 本轮初步归纳

- 机构管理需要把“租户”作为系统顶层边界，把“院区、科室”作为可选组织层级处理。
- 机构管理不仅影响组织结构，也影响患者归属、人员归属、数据归属、数据权限和 C 端入口。
- 下一步可继续展开机构管理的复杂兼容场景，再进入科室管理。

### 轮次 11：组织管理 - 机构管理细化

- 业务表达上确认：机构在系统中等于租户，后续行文统一以“机构”表达这一实体。
- 现有系统实际是租户对齐院区层级，这是一个重大改造点。
- 目标层级关系应调整为：机构对齐租户，院区作为机构下级层级。
- 集团、区域性组织、医联体等属于租户上级层级，可关联多个机构。
- 租户上级层级只做数据查询、统计和管理关联，不参与实际业务执行。
- 一个机构对应一个小程序，即一个 C 端入口。
- 不存在多机构共用小程序，也不存在一个机构对应多个小程序入口。
- M 端已有基础租户信息管理功能，当前主要包含名称、key、开通功能模块等基础信息。
- 机构之间允许数据共享，是否共享主要由业务侧决策。
- 暂时不考虑跨机构协作、跨机构查看和平台代运营查看，但未来不排除。

### 本轮初步归纳

- 主文档中的组织管理专题已调整为“模块总览 + 子模块”的结构。
- 机构管理子模块已按“已确认业务背景、对系统的影响、功能改造项、待确认问题”沉淀。
- 功能改造项暂定使用表格记录，字段为：功能点、改造内容、优先级、为什么需要。
- 机构管理当前明确的高优先级改造项是“租户层级重构”。
- 机构信息管理优化暂列低优先级。
- 机构级系统配置范围仍不明确，已移入待确认问题。

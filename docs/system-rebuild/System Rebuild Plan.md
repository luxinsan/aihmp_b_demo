# 患者数据中心与全链路升级改造推进排期建议

## 1. 文档定位

本文用于梳理“患者数据中心 / 健康档案数据中心”及其关联业务的一轮全面系统升级改造节奏，重点回答：

- 哪些能力必须先做，哪些业务功能可以后置并行。
- 数据中心、信息采集、健康方案、预警监测、C 端体验、AI 助手之间的依赖关系。
- 建议如何分阶段推进，降低大改造对现有业务演示和交付的冲击。

本文是推进排期建议，不替代各模块 PRD。后续每个业务功能仍建议按独立需求进入详细 PRD、设计、研发、测试和验收流程。

## 2. 总体推进原则

### 2.1 数据基建先行

本轮升级的核心不是单点页面改造，而是建立可持续扩展的患者档案数据中心。建议先完成以下底座，再推进复杂 AI 和业务闭环：

- 外部系统数据获取与保存机制。
- 数据清洗、结构化、指标映射和有限落表策略。
- 面向业务侧的统一档案数据接口。
- 常规指标库、重点指标库和管理主题之间的关系模型。

### 2.2 业务能力分层交付

建议把业务拆为三层：

- 基础能力层：数据中心、问卷/量表、指标库、标签、任务、消息触达。
- 管理配置层：分组、健康方案、预警策略、租户/团队开关配置。
- 用户体验层：C 端建档、档案、信息采集、AI 助手、任务执行、报告查看。

基础能力层尽量先稳定，管理配置层分批开放，用户体验层按核心链路逐步替换。

### 2.3 AI 场景不直接绑定一期大交付

AI 能力依赖数据质量、知识库、结构化接口和任务闭环。建议采用“先规则和结构化链路、再 AI 增强”的节奏：

- 一期先让数据、指标、任务、预警、报告具备稳定输入输出。
- 二期接入 AI 生成、AI 总结、AI 问答和 AI 辅助配置。
- 三期验证模型能力后，再推进智能分组、定向调阅、个性化干预和多轮语音采集。

## 3. 工作包拆分

### 3.0 工作包概要

| 工作包 | 标题              | 核心目标                         |
| --- | --------------- | ---------------------------- |
| WP1 | 患者档案数据中心        | 定义健康档案数据中心架构与能力模块，形成统一数据底座   |
| WP2 | 信息采集与问卷量表底座     | 覆盖筛查、风险评估、分组、管理过程信息采集等场景     |
| WP3 | 患者管理与分组         | 统一患者分组能力，兼容院内场景和泛健康管理场景      |
| WP4 | 健康方案、打卡与重点指标    | 以健康管理主题作为核心锚点，重构方案、打卡和效果评估能力 |
| WP5 | 预警监测与干预闭环       | 从单一量表监控升级为基于数据中心的预警监控与干预任务闭环 |
| WP6 | C 端建档、档案与健康风险展示 | 适配不同租户建档要求，承接数据中心和预警体系       |
| WP7 | C 端体验层与任务执行     | 重构 C 端功能框架，形成健康管理任务执行主链路     |
| WP8 | C 端 AI 助手 / 客服  | 升级为 C 端全场景对话式交互入口            |

### 3.1 WP1 患者档案数据中心

目标：定义健康档案数据中心架构与能力模块，形成统一数据底座。

范围：

- 外部系统数据接入、保存、更新、幂等和来源追踪。
- 原始数据区、清洗数据区、业务结构化数据区的边界。
- 按业务需求有限落表，避免一次性过度建模。
- 档案数据统一查询接口。
- 指标、报告、任务、预警、分组等业务对档案数据的调用规范。

关键产物：

- 数据中心架构设计。
- 外部数据接入协议与字段映射规则。
- 数据清洗和落表策略。
- 统一档案数据 API 设计。
- 数据质量、数据来源、更新时间、租户隔离策略说明。

### 3.2 WP2 信息采集与问卷量表底座

目标：覆盖筛查、风险评估、分组、管理过程信息采集等场景。

范围：

- 问卷基础能力升级。
- 专门题型拓展。
- 题目可配置对应采集数据指标。
- 问卷下发到 C 端场景。
- 支持持续多次填写。
- 支持选择是否生成评估报告。
- 报告同步显示到 B 端。
- 预留 AI 助手文本/语音采集入口。

依赖：

- 与 WP1 的采集指标映射、结构化入库、档案回写强相关。
- 与 WP7 的 C 端入口、路径和交互强相关。

### 3.3 WP3 患者管理与分组

目标：统一患者分组能力，兼容院内场景和泛健康管理场景。

范围：

- 患者疾病标签、风险标签。
- 按标签入组和展示。
- 分组方式收敛为统一模块。
- 租户级、团队级分组开关配置。
- 智能分组的输入条件和人工确认机制。

建议：

- 一期先做规则分组和标签入组。
- 智能分组作为 AI 增强能力，在数据中心和标签体系稳定后接入。

### 3.4 WP4 健康方案、打卡与重点指标

目标：以健康管理主题作为核心锚点，重构方案内容结构、打卡底层逻辑和阶段/结营效果评估能力。

范围：

- 增加健康管理主题概念。
- 方案结构升级为：主任务链 + 打卡 + 预警 + 重点指标。
- 打卡功能底层逻辑重构，包括打卡项定义、打卡频率、打卡周期、补打规则、完成判定、异常记录和统计口径。
- 打卡与方案、任务、重点指标、预警、效果评估建立关联。
- 建立常规指标库。
- 建立主题/病种维度的重点指标组合。
- 指标数据可视化，优先读取结构化库表数据。
- 建立阶段或结营管理效果评估能力，支持按管理主题汇总目标达成、指标变化、任务完成、打卡表现和风险变化。
- 关联资源内容拓展。
- 预留基于知识库的 AI 生成能力。

依赖：

- 与 WP1 的指标清洗和结构化落表强相关。
- 与知识库专项强相关，AI 生成不建议阻塞一期方案结构升级。

### 3.5 WP5 预警监测与干预闭环

目标：从单一量表监控升级为基于数据中心的预警监控与干预任务闭环。

范围：

- 以方案或团队维度配置预警。
- 支持全局性监控和个体化监控。
- 多级预警策略。
- 触达策略配置。
- 支持 AI 基于知识库生成策略。
- 基于数据中心扫描量表、指标、打卡、任务等数据。
- 从预警任务到下发干预任务的完整链路。
- 干预任务完成状态追踪。

建议：

- 一期先支持规则预警、人工配置策略和干预任务下发。
- 二期再接入 AI 策略生成和模型扫描。

### 3.6 WP6 C 端建档、档案与健康风险展示

目标：适配不同租户建档要求，移除不贴合业务的信息，承接数据中心和预警体系。

范围：

- 按租户配置建档字段。
- 可配置是否对接院内系统建档。
- 健康档案资料分类与分类规则可配置。
- 按业务场景隐藏或移除不适用信息，如健康评分、档案完成率。
- 健康风险监测、识别、提示展示。
- 预留数字孪生式风险表现层。

依赖：

- 与 WP1 数据来源、租户隔离、档案结构强相关。
- 与 WP5 风险识别和预警体系强相关。

### 3.7 WP7 C 端体验层与任务执行

目标：重构 C 端功能框架，保证后续扩展性，并形成健康管理任务执行主链路。

范围：

- 纯前端层整体改造。
- 梳理 C 端功能框架、路由、入口和边界。
- 信息采集入口、填报、结果查看。
- 任务下发、触达、执行、反馈链路。
- 多场景触达能力。
- 关联企微体系。

建议：

- C 端不要只按页面重做，应按“建档 - 采集 - 方案 - 任务 - 打卡 - 预警 - 报告”链路重做。
- 当前仓库已有 `patient-mobile-h5 + patient-web-preview` 主链路，后续 C 端需求应继续收敛到该链路。

### 3.8 WP8 C 端 AI 助手 / 客服

目标：升级为 C 端全场景对话式交互入口。

范围：

- 全场景入口定位。
- 主动打招呼、下发消息、提示引导。
- 归集消息通知能力。
- 查询档案、报告、任务、进度。
- 信息采集、任务执行、打卡等交互能力。
- 信息采集问题转化更拟人化。
- 文本和语音交互。
- 租户后台可配置能力整合。
- 明确多租户隔离和数据归档策略。

建议：

- 一期先做“助手入口 + 文本交互 + 查询和引导”。
- 二期做“信息采集和任务执行”。
- 三期再做“语音交互全面升级”和更强主动触达。

## 4. 建议阶段排期

以下按 16 周主计划估算，适合中大型升级。若资源不足，建议拆为两个 8 周版本，不建议压缩为一个短迭代完成。

### 阶段 0：方案收敛与技术预研，建议 1-2 周

目标：

- 明确本轮升级边界。
- 确认数据中心总体架构。
- 梳理外部系统、C 端、B 端、AI、知识库、企微的依赖。
- 输出项目级里程碑和模块 PRD 列表。

重点任务：

- 建立患者档案数据中心顶层设计。
- 明确租户隔离原则。
- 明确常规指标库、重点指标库、健康管理主题的关系。
- 明确哪些 AI 场景进入一期，哪些后置。
- 评估语音交互和模型定向调阅能力。

交付物：

- 数据中心概要设计。
- 升级范围清单。
- 一期 MVP 范围。
- 模块 PRD 拆分清单。

### 阶段 1：数据中心与指标底座，建议 3-4 周

目标：

- 完成数据中心最小可用底座。
- 为信息采集、指标可视化、分组、预警、报告生成提供统一数据接口。

重点任务：

- 外部数据获取和保存机制。
- 数据清洗和有限落表规则。
- 统一档案数据接口。
- 常规指标库和重点指标库初版。
- 主题/病种与指标关系模型。
- 数据来源、更新时间、租户隔离策略。

交付物：

- 数据中心 MVP。
- 指标库 MVP。
- 统一档案数据 API。
- 数据接入和清洗规则文档。

### 阶段 2：信息采集、标签分组与建档能力，建议 3 周

目标：

- 让数据进入系统的路径可配置、可复用。
- 支持筛查、风险评估、分组和管理过程采集。

重点任务：

- 问卷题型拓展。
- 题目与采集指标映射。
- 问卷下发配置。
- 多次持续填写。
- 是否生成评估报告配置。
- B 端报告同步展示。
- 患者疾病/风险标签。
- 规则分组和按标签入组。
- 租户建档字段配置。

交付物：

- 信息采集 MVP。
- 量表/问卷底座升级。
- 标签和规则分组 MVP。
- 租户建档字段配置 MVP。

### 阶段 3：健康方案、打卡、任务链与预警闭环，建议 4 周

目标：

- 建立以健康管理主题为核心的管理框架。
- 打通方案、任务、打卡、指标、预警、干预任务和效果评估。

重点任务：

- 健康管理主题模型。
- 方案结构升级。
- 主任务链、打卡、重点指标、预警配置。
- 打卡功能底层逻辑重构。
- 指标可视化。
- 方案/团队维度预警配置。
- 多级预警和触达策略。
- 预警生成干预任务。
- 干预任务状态追踪。
- 阶段或结营效果评估规则与结果展示。

交付物：

- 健康方案结构升级版。
- 打卡功能重构版。
- 重点指标展示与可视化。
- 预警监测 MVP。
- 干预任务闭环 MVP。
- 阶段或结营效果评估 MVP。

### 阶段 4：C 端体验与 AI 助手融合，建议 3 周

目标：

- 以 C 端主链路承接前面所有管理能力。
- 让患者侧形成清晰、连续、可执行的健康管理体验。

重点任务：

- C 端功能框架和页面链路重构。
- 建档、档案、风险提示展示。
- 信息采集入口和结果查看。
- 任务触达、执行、打卡。
- AI 助手入口收敛。
- AI 助手查询档案、报告、任务、进度。
- AI 助手辅助信息采集的文本交互。
- 租户后台助手能力开关整合。

交付物：

- C 端主链路升级版。
- AI 助手文本交互 MVP。
- 任务执行链路升级版。
- 体验验收清单。

### 阶段 5：AI 增强、联调验收与灰度，建议 2-3 周

目标：

- 验证 AI 场景效果。
- 完成跨模块联调、数据回归和灰度准备。

重点任务：

- 智能分组能力验证。
- 信息采集预填写。
- 健康自测与评估报告生成。
- 春晓场景报告文档生成。
- 个案管理场景方案与资源生成。
- 个性化生活方式干预任务。
- 打卡分析与评价。
- 智能预警监测和预警干预增强。
- 依从性总结分析。
- 阶段或结营管理效果智能分析。

交付物：

- AI 场景验证报告。
- 全链路联调报告。
- 灰度发布方案。
- 运营和租户配置手册。

## 5. 推荐 MVP 边界

建议一期 MVP 聚焦以下闭环：

1. 患者数据中心可以接入、保存、清洗、查询基础档案和关键健康指标。
2. 信息采集可以通过问卷/量表进入数据中心，并按指标映射结构化。
3. B 端可以配置健康管理主题、重点指标、基础方案、打卡规则和任务。
4. 预警可以基于结构化指标和量表结果进行规则监控。
5. 预警可以触发干预任务，并追踪完成状态。
6. C 端可以完成建档、信息采集、查看任务、执行任务、打卡和查看结果。
7. 管理端可以基于指标变化、任务完成和打卡表现形成阶段或结营效果评估。
8. AI 助手先作为统一入口，支持查询、引导和文本式信息采集，不把高复杂语音和强智能分组作为一期硬交付。

## 6. 关键依赖关系

| 依赖项        | 被影响模块                   | 建议处理方式                |
| ---------- | ----------------------- | --------------------- |
| 数据中心架构未定   | 信息采集、指标、预警、报告、AI        | 阶段 0 必须先冻结 MVP 架构     |
| 指标库未定      | 健康方案、打卡、重点指标、预警、可视化     | 阶段 1 建立常规指标库和主题指标关系   |
| 租户隔离未定     | C 端建档、AI 助手、数据归档、外部系统接入 | 阶段 0 明确原则，阶段 1 落到数据模型 |
| 知识库专项未完成   | AI 生成方案、AI 预警策略、资源推荐    | 一期先预留接口，AI 生成作为后置增强   |
| 企微体系未明确    | 任务触达、预警触达、消息通知          | 阶段 3 前完成触达方案选型        |
| 语音能力技术难度未知 | AI 助手、信息采集体验            | 阶段 0 做技术预研，避免阻塞主链路    |

## 7. 风险与建议

### 7.1 最大风险：所有模块同时开工但底层口径不一致

建议先冻结以下口径：

- 患者唯一身份和多租户归属。
- 档案数据分层和来源追踪。
- 指标编码、单位、范围、更新时间。
- 题目与指标映射关系。
- 任务、打卡、预警、干预任务、阶段评估之间的状态模型。

### 7.2 AI 场景风险：效果依赖数据质量和知识库成熟度

建议每个 AI 场景都定义兜底策略：

- 可人工编辑。
- 可追溯引用数据来源。
- 可关闭或按租户开关。
- 生成结果可二次确认后再下发给 C 端。

### 7.3 C 端风险：入口过多导致体验再次分散

建议用 AI 助手和任务中心收敛入口：

- 信息采集、任务执行、打卡、报告查看都可以从助手或任务中心进入。
- 复杂业务不要直接堆页面，应通过管理主题和当前阶段组织。

### 7.4 排期风险：不建议把语音、强智能分组、模型全量扫描放入一期

这些能力技术和效果不确定性较高，建议作为增强包：

- 语音采集增强包。
- 智能分组增强包。
- AI 预警策略增强包。
- 生活方式个性化干预增强包。

## 8. 建议优先级

### P0 必做

- 患者档案数据中心 MVP。
- 外部数据保存、清洗、有限落表。
- 统一档案数据接口。
- 指标库和主题指标关系。
- 问卷/量表题目与指标映射。
- 健康管理主题和方案结构升级。

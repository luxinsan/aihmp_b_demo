## 2. 系统重构背景

当前演示前端壳与真实系统现状存在明显差距，不能直接作为目标系统功能框架的依据。系统重构需要从真实业务现状出发，重新梳理顶层信息架构。

第一轮调研已确认：

- 当前系统分为平台管理端、医护端、患者端三类端。
- 平台管理端当前能力较弱，主要只有租户基础信息管理。
- 医护端是当前业务管理闭环的主要操作端。
- 患者端真实形态为小程序。
- 健康管理方案是健康管理业务最核心的对象或手段。
- 患者数据来源是多源数据，需要健康数据中心作为统一底座。
- C 端 AI 助手定位为围绕健康管理的全场景助手。
- 本轮重构主要目标是信息架构重构。

## 3. 框架设计原则

本系统功能框架采用“三端 + 能力分层 + 业务主轴 + 核心对象 + 横向治理”的组织方式。

- 以真实业务现状为起点：当前前端壳只作参考，不作为目标系统功能范围依据。
- 以健康管理闭环为主轴：系统不按孤立菜单堆叠，而按患者建档、数据汇聚、方案制定、任务执行、预警干预、阶段评估和 AI 辅助组织。
- 以健康数据中心为底座：健康数据中心是全系统基础设施，不是某一端的普通页面模块。
- 以健康管理方案为业务编排对象：方案负责组织任务、问卷、文章、指标、预警、随访、评估和 AI 生成依据。
- 以患者服务体验为闭环终点：B 端管理能力最终应落到 C 端提醒、查看、执行、反馈、查询和归档体验。
- 以 AI 能力贯穿业务流程：AI 助手应覆盖查询、生成、任务执行、自动归档、提醒和依据追溯。
- 以横向治理约束全系统：多租户隔离、权限、数据安全、审计、资源版本、发布审核和 AI 治理应贯穿所有模块。

```text
患者建档
-> 健康数据汇聚
-> 健康管理方案制定 / 分配
-> 任务执行
-> 预警与干预
-> 阶段评估 / 结营评估
-> AI 辅助查询 / 生成 / 执行 / 归档
```

## 4. 系统总体定位

AI HMP 是面向医院或机构租户的健康管理系统，围绕患者健康数据、健康管理方案、任务执行、资源配置和 AI 辅助能力，支撑医护团队和患者之间形成持续健康管理闭环。

系统不应被理解为单纯的患者档案系统、任务系统、内容系统或 AI 聊天系统，而应被定义为：

> 以健康数据中心为底座，以健康管理方案为核心组织方式，以任务执行为服务闭环，以知识库和 AI 助手为智能增强能力的多租户健康管理平台。

行业校验结论：

- 国家卫健委《“十四五”全民健康信息化规划》强调互联互通、标准体系、数字健康服务、数据资源治理和安全保障，支撑健康数据中心和标准数据体系作为底层能力。
- 国务院《关于促进“互联网+医疗健康”发展的意见》强调线上线下协同、电子健康档案查询、家庭医生服务和人工智能应用，支撑 B/C 端联动和患者服务层建设。
- WHO 数字健康和以人为中心整合服务相关框架强调以人为中心、连续服务、跨专业协作、数据治理和互操作能力，支撑本系统按能力架构而非菜单堆叠组织。
- HL7 FHIR 中 Patient、CarePlan、Task、Questionnaire 等资源模型，与本文抽象出的患者、健康管理方案、任务、问卷等核心对象基本一致。

## 5. 系统分端架构

### 5.1 平台管理端

别名：

- M 端。
- 平台 M 端。

服务对象：

- 平台管理人员。
- 平台实施或运营人员。

已确认事实：

- 当前真实功能非常薄弱，主要只有租户基础信息管理。
- 该能力本质上是创建基础租户账号。
- 当前各种配置与管理仍然高度依赖人工配置和部署。

目标态建议：

- M 端应逐步承担平台级治理能力，包括租户、平台资源、平台配置、AI 能力、运营统计和审计。
- M 端需要区分平台侧能力和租户侧能力，不应与 B 端租户管理混淆。

待确认问题：

- 当前人工配置和部署中，哪些事项必须产品化进入 M 端。
- 平台是否需要管理租户套餐、功能开关、资源授权和 AI 调用配置。
- 平台人员是否允许代租户操作，若允许是否需要审计。

### 5.2 医护端

别名：

- B 端。
- 医护工作站。
- 各个租户的工作站。

服务对象：

- 医生。
- 护士。
- 健康管理师。
- 医院或机构领导。

已确认事实：

- B 端主要功能包括患者管理、任务管理、配置管理、组织管理，以及登录和个人中心等基础能力。
- B 端是当前业务管理闭环的主要操作端。

推导结论：

- B 端应同时满足一线执行、健康管理服务、管理监督三类视角。
- B 端信息架构不能只按后台配置菜单组织，还需要围绕患者、方案、任务和风险形成业务工作台。

### 5.3 患者端

别名：

- C 端。
- 患者端。
- 各个租户的用户端。
- 小程序。

服务对象：

- 患者。
- 居民。
- 健康管理服务对象。

已确认事实：

- 真实系统形态为小程序。
- 当前演示前端壳使用 H5 形态可以接受。
- 主要模块包括首页、健康管理、我的。
- C 端 AI 助手主要面向患者，是围绕健康管理的全场景助手。

推导结论：

- C 端应围绕“提醒 - 查看 - 执行 - 反馈 - 查询 - 归档”的患者服务链路组织。
- AI 助手不应只作为一个聊天入口，而应成为健康管理全场景交互能力。

## 6. 顶层能力分层

系统目标态可按六层纵向能力和一组横向治理能力组织。

```text
AI HMP 顶层能力分层

1. 平台治理层
2. 业务管理层
3. 资源配置层
4. 数据底座层
5. 患者服务层
6. AI 能力层

横向治理能力：多租户隔离 / 权限 / 审计 / 安全 / 版本 / 发布 / AI 治理
```

### 6.1 平台治理层

定位：

- 管理多租户体系和平台级公共能力。

目标态能力：

- 租户管理。
- 平台资源管理。
- 平台配置管理。
- 平台 AI 能力管理。
- 资源分发与授权。
- 运营统计。
- 审计日志。

当前现状：

- 当前仅有非常基础的租户信息管理。

### 6.2 业务管理层

定位：

- 支撑医护端健康管理服务闭环。

目标态能力：

- 工作台。
- 患者管理。
- 健康管理方案。
- 任务管理。
- 预警与干预。
- 报告与评估。
- 组织管理。

推导结论：

- 业务管理层是 B 端的核心。
- 健康管理方案和任务管理是贯穿 B 端与 C 端的主轴。

### 6.3 资源配置层

定位：

- 为健康管理方案、任务执行和 AI 生成提供可复用资源。

目标态能力：

- 方案模板。
- 任务模板。
- 问卷资源。
- 文章 / 宣教资源。
- 知识库。
- 指标库。
- 标签 / 分组规则。
- 预警策略。
- 消息模板。

已确认事实：

- 问卷、文章、知识库都是服务于健康管理方案的资源。
- 知识库还会作为各种 AI 生成结果的重要依据。

待确认问题：

- 资源是平台统一维护、租户维护，还是平台与租户两级共存。
- 资源是否需要审核、发布、版本、引用追踪。
- 平台资源与租户资源之间是继承、复制、引用还是独立维护。

### 6.4 数据底座层

定位：

- 统一接收、保存、加工、标准化和服务患者相关健康数据。

参考文档：

- `docs/product-planning/health-data-center-product-solutions.md`

已确认事实：

- 患者数据来源为多源数据。
- 健康数据中心应作为多源健康数据的统一底座。

目标态能力：

- 多源数据接入。
- 原始数据管理。
- 数据处理。
- 标准数据体系。
- 数据服务。
- 安全管控与使用留痕。

推导结论：

- 健康数据中心不是单独业务页面，而是支撑患者管理、方案制定、任务执行、预警评估、报告生成和 AI 助手的底座能力。
- 数据服务需要向不同业务场景提供统一口径，同时保留来源、时间、采集方式和使用留痕。

### 6.5 患者服务层

定位：

- 面向患者提供健康管理服务入口和任务执行体验。

目标态能力：

- 患者首页门户。
- 健康管理。
- 健康任务。
- 健康方案。
- 健康档案。
- 消息与提醒。
- 我的。
- C 端 AI 助手。

推导结论：

- 患者服务层应以患者最重要的待办、提醒、方案和 AI 助手为核心，而不是简单罗列功能入口。

### 6.6 AI 能力层

定位：

- 贯穿 M/B/C 三端的智能辅助能力，其中 C 端 AI 助手是当前已明确的重要方向。

已确认事实：

- C 端 AI 助手是围绕健康管理的全场景助手。
- 覆盖问答、查询、执行任务、自动归档等能力。
- 知识库是 AI 生成结果的重要依据。

目标态能力：

- 问答。
- 查询。
- 内容生成。
- 方案辅助。
- 任务执行引导。
- 自动归档。
- 提醒与主动触达。
- AI 生成依据追溯。

待确认问题：

- AI 结果是否需要医护审核。
- AI 是否可以直接修改任务、方案或档案。
- AI 操作记录是否进入审计和患者服务记录。

### 6.7 横向治理能力

定位：

- 对 M/B/C 三端、数据底座、资源配置和 AI 能力形成统一约束。
- 横向治理能力不是单个菜单，而是系统级规则集合。

目标态能力：

- 多租户隔离。
- 角色权限。
- 数据权限。
- 操作审计。
- 数据安全与隐私授权。
- 资源版本管理。
- 内容审核与发布。
- 配置变更留痕。
- AI 生成依据追溯。
- AI 操作归档与审计。

推导结论：

- 多租户隔离必须贯穿租户、患者、组织、资源、数据、任务和 AI 会话。
- 权限体系需要同时覆盖功能权限和数据权限。
- 资源类对象需要考虑发布、停用、版本、复制、引用和回滚。
- AI 能力需要将生成依据、执行动作、归档结果和人工审核状态纳入治理。

待确认问题：

- 当前系统已有的权限模型粒度。
- 租户是否允许自定义角色和数据权限。
- AI 操作是否需要与普通人工操作同等审计。

## 7. 三端功能框架

本节先聚焦 B 端与 C 端功能框架。当前阶段重点是踩准功能颗粒度，不展开到增删改查等操作级能力。M 端当前仅保留现状说明，后续再单独展开。

### 7.1 M 端功能框架

当前真实功能：

```text
M 端 / 平台管理端
- 登录
- 租户管理
  - 租户基础信息管理
  - 基础租户账号创建
```

暂不展开：

- M 端当前不是本轮功能框架梳理重点。
- 当前仅确认租户基础信息管理能力。
- 平台治理、资源下发、AI 配置、运营审计等目标态能力后续单独梳理。

### 7.2 B 端功能框架

菜单-页面框架初稿：

```text
B端 / 医护工作站
- 工作台

- 患者管理
  - 全部患者
  - 在管患者

- 任务中心

- 配置中心
  - 方案模板
  - 问卷量表
  - 宣教内容
  - 管理主题

- 知识管理

- 组织管理

- 系统管理
```

功能定义约束：

- 工作台是信息聚合入口，不是业务主数据模块。
- 工作台后续单独设计，当前不展开子菜单页面。
- 工作台数据来源于患者管理、任务中心、配置中心、知识管理、组织管理、系统管理等底层业务功能。
- 健康管理是 B 端系统的业务母题，不作为普通一级菜单。
- 患者管理承载健康管理服务对象，当前只保留全部患者、在管患者两个稳定页面。
- 患者分组更适合作为患者列表场景中的动作、筛选维度或入组结果，不先作为独立菜单。
- 患者档案暂不作为患者管理下的独立菜单，后续结合患者详情页和患者方案实例呈现方式再确定。
- 任务中心暂不展开子项，后续回到健康管理方案体系中统一梳理执行、跟踪、信息采集、宣教、打卡、预警干预等边界。
- 配置中心承载健康管理开展前的前置资产，当前阶段包括方案模板、问卷量表、宣教内容、管理主题。
- 方案模板匹配患者后生成患者方案实例。
- 患者方案实例主要在患者档案中呈现，不单独作为当前一级功能。
- 知识管理聚焦知识库及专业依据管理，区别于配置中心中的问卷量表和宣教内容。
- 组织管理承载租户内部组织、科室、团队、人员等管理能力。
- 系统管理承载角色权限、基础字典、业务参数、消息通道、数据同步、日志等系统基础能力；后续可继续拆分。
- AI 不单独作为一级菜单，应嵌入患者管理、任务中心、配置中心、知识管理等业务场景。
- 当前功能框架只定义功能颗粒度，不展开常规增删改查能力。

### 7.3 C 端功能框架

功能框架初稿：

```text
C端 / 患者小程序
- 首页
  - 重要事项
  - 今日任务
  - 健康方案摘要
  - AI 助手
  - 服务入口

- 健康管理
  - 当前方案
  - 健康任务
  - 打卡记录
  - 问卷记录
  - 指标记录
  - 阶段反馈
  - 历史方案

- AI 助手
  - 健康问答
  - 档案查询
  - 方案查询
  - 任务引导
  - 指标解读
  - 自动归档

- 健康档案
  - 基础档案
  - 健康数据
  - 检查检验
  - 问卷记录
  - 报告记录

- 消息提醒
  - 任务提醒
  - 预警提醒
  - 医护消息
  - 系统通知

- 我的
  - 个人信息
  - 家庭成员
  - 绑定机构
  - 授权隐私
  - 设置
  - 帮助客服
```

待确认问题：

- C 端首页首屏最重要的内容排序。
- 健康管理页按方案组织，还是按任务组织。
- AI 助手是独立一级入口，还是同时嵌入首页和任务场景。
- AI 自动归档结果在 C 端是否对患者可见。

## 8. 核心业务主轴

系统目标态不应只是三端菜单集合，而应围绕健康管理闭环组织。

```text
租户开通
-> 组织与人员配置
-> 患者建档
-> 多源健康数据汇聚
-> 健康管理方案制定 / 分配
-> 生成任务
-> 患者执行 / 医护跟进
-> 预警与干预
-> 阶段评估 / 结营评估
-> AI 辅助查询 / 生成 / 执行 / 归档
```

### 8.1 租户开通主轴

涉及端：

- M 端。
- B 端。

目标态流程：

```text
平台创建租户
-> 初始化租户账号
-> 配置组织 / 科室 / 人员 / 权限
-> 分配平台资源
-> 配置 C 端入口
-> 租户开始使用
```

当前差距：

- 当前 M 端仅能完成基础租户账号创建，后续配置仍依赖人工。

### 8.2 患者健康管理主轴

涉及端：

- B 端。
- C 端。
- 数据底座。
- AI 能力层。

目标态流程：

```text
患者建档
-> 健康数据汇聚
-> 健康评估
-> 制定 / 分配健康管理方案
-> 生成任务
-> 患者执行任务
-> 医护跟进
-> 数据回写
-> 预警 / 干预
-> 阶段评估
```

推导结论：

- 健康管理方案是该主轴的核心组织方式。
- 任务是方案落地执行的载体。
- 数据中心是方案制定、预警和评估的基础。

### 8.3 AI 辅助主轴

涉及端：

- 重点是 C 端。
- 未来可扩展到 B 端和 M 端。

目标态流程：

```text
获取患者档案 / 方案 / 任务 / 知识库上下文
-> AI 问答 / 查询 / 引导 / 生成
-> 患者执行或医护确认
-> 结果归档
-> 进入任务、档案或服务记录
```

待确认问题：

- AI 自动归档的归档对象是什么。
- AI 执行任务后，是否等同于患者完成任务。
- AI 是否需要区分“建议”和“已执行动作”。

## 9. 核心业务对象

后续系统信息架构应围绕以下核心业务对象组织。

| 对象 | 定位 | 说明 |
| --- | --- | --- |
| 租户 | 多租户边界对象 | 核心锚点为医院或机构。 |
| 组织 | 租户内部管理结构 | 包括科室、团队、人员、角色权限。 |
| 患者 | 健康管理服务对象 | B 端管理和 C 端服务的核心对象。 |
| 健康数据 | 健康管理事实基础 | 多源进入健康数据中心，支撑业务复用。 |
| 健康管理方案 | 核心业务对象 | 健康管理的核心手段，关联患者后生成任务。 |
| 任务 | 执行闭环载体 | 承接方案、提醒、干预、随访和患者执行。 |
| 问卷 | 方案服务资源 | 可作为信息采集、评估和任务执行内容。 |
| 文章 | 方案服务资源 | 可作为宣教、任务和患者端内容。 |
| 知识库 | AI 与业务依据资源 | 服务方案，也作为 AI 生成结果依据。 |
| 预警 | 风险识别对象 | 基于数据、任务、方案等触发干预。 |
| 报告 / 评估 | 阶段性结果对象 | 用于评估、复盘、结营和医患沟通。 |
| AI 助手 | 智能交互能力 | 面向 C 端健康管理全场景，支持问答、查询、执行、归档。 |

### 9.1 关键对象关系

```text
租户
-> 组织 / 科室 / 团队 / 人员 / 角色
-> 患者
-> 健康数据
-> 健康管理方案
-> 任务
-> 执行记录 / 打卡 / 问卷记录 / 指标录入
-> 预警 / 干预
-> 报告 / 阶段评估 / 结营评估
```

资源对象关系：

```text
方案模板
-> 患者健康管理方案实例
-> 任务实例
-> 引用问卷 / 文章 / 知识库 / 指标 / 预警策略
```

AI 对象关系：

```text
患者档案 + 健康数据 + 患者方案 + 任务 + 知识库
-> AI 会话 / AI 生成记录
-> 查询结果 / 建议 / 任务执行引导 / 自动归档
-> 服务记录 / 任务记录 / 审计记录
```

### 9.2 模板与实例关系

目标态建议：

- 方案模板是可复用配置对象。
- 患者健康管理方案实例是模板分配给患者后的个体化执行对象。
- 任务模板是方案中的执行动作定义。
- 任务实例是面向医护或患者的具体执行记录。
- 问卷、文章、知识库、指标、预警策略作为资源被方案模板或患者方案实例引用。

待确认问题：

- 模板更新后，已生成的患者方案实例是否跟随更新。
- 患者方案实例是否允许医护个性化调整。
- 资源被引用后，是否锁定版本。
- 知识库更新是否影响历史 AI 生成依据追溯。

### 9.3 总体待确认问题

- 健康管理方案是否需要区分模板、患者方案实例和执行计划。
- 任务是否需要统一抽象为医护任务和患者任务的父对象。
- 知识库是否存在平台级和租户级两套资源边界。

# 系统排查梳理说明

## 目标

通过核心业务命题专题排查，先梳理业务背景、对象关系、系统功能改造、当前问题和待确认事项。当前阶段不提前维护应修清单和迭代路线图，待信息明确后再统一制定。

## 文档结构

- [00-known-business-knowledge.md](./00-known-business-knowledge.md)：从既有系统重建文档提炼出的已知业务知识。
- [02-system-review-master.md](./02-system-review-master.md)：系统边界、核心业务命题专题。
- [05-interview-notes.md](./05-interview-notes.md)：访谈与排查过程原始记录。

## 排查原则

1. 先按核心业务命题做专题排查，再识别医护端（B 端）、患者端（C 端）和底座职责。
2. 先记录现象和业务影响，再判断技术归因。
3. 当前阶段只记录问题线索，不提前编号、定级和排期。
4. 后续统一制定清单时，再按业务影响、用户影响、数据风险、交付依赖判断优先级。
5. 已在 `00-known-business-knowledge.md` 明确的事实，不再作为开放问题重复调研。
6. 分端命名统一遵守根目录 `TERMINOLOGY.md`。

## 文档维护原则

1. 结构优先：只保留必要章节，不堆临时过程。
2. 内容概要化：写结论、对象关系、关键规则和问题线索，不写长篇解释。
3. 推导优先：先沉淀业务事实，再说明系统影响，最后归纳功能改造项。
4. 专题结构：大专题保留模块总览，再按子模块拆分子章节。
5. 子模块结构：每个子模块按已确认业务背景、对系统的影响、功能改造项、待确认问题沉淀。
6. 功能改造项：优先使用表格记录，字段为功能点、改造内容、优先级、为什么需要；每行只描述一个具体改造内容。
7. 分点描述：各章节使用圆点项目符号；每点表达一个完整事实或判断，可合并的事实应整合表达，避免过碎，也不写成长段文本。
8. 不提前清单化：当前不编号、不定级、不排期。
9. 不重复沉淀：已有结论只更新，不在多处重复展开。
10. 每轮只补关键增量：对话细节先提炼，再进入文档。

查阅顺序：

1. 系统边界与能力分层
2. 核心业务命题专题

### 1.5 核心业务闭环

当前排查主线：患者通过院内 API 拉取或 C 端注册进入统一患者池，经患者建档 / 绑定、标签 / 分组、健康管理方案制定、健康任务执行、数据监测、预警触发与处理，最终形成健康管理服务闭环。

挂起事项：当前系统没有“目标人群”概念，统一称为患者；筛选识别业务定位暂不明确，本轮先挂起，不作为当前主流程起点。

既有文档中的目标态主线：

```text
租户开通
-> 组织与人员配置
-> 患者建档
-> 多源健康数据汇聚
-> 健康管理方案制定 / 分配
-> 生成任务
-> 患者执行 / 医护跟进
-> 预警与干预
-> 阶段评估 / 结营评估
-> AI 辅助查询 / 生成 / 执行 / 归档
```

## 2. 核心业务命题专题

### 2.1 排查方法

后续排查不再只按 B/C 二元结构或线性流程推进，而是按核心业务命题做立体拆解。当前优先使用推导式结构：

- 模块总览：说明模块边界和核心矛盾。
- 已确认业务背景：记录已确认的业务事实。
- 对系统的影响：说明业务事实对系统模型、流程、权限和数据的影响。
- 功能改造项：从系统影响推导出需要改造和增强的功能。
- 待确认问题：记录尚未确认的问题，不提前展开为应修清单。

专题下先补充业务事实，再推导系统影响和功能改造方向。待确认问题先简单列出，后续 review 时逐步确认。

内容跨度较大的专题，可保留模块总览，再按子模块拆分子章节；每个子模块继续沿用业务事实、系统影响、改造增强、待确认问题的推导结构。

### 2.2 患者管理专题

#### 2.2.1 专题定位

- 患者管理不是单一页面，也不是单纯的患者列表。
- 患者管理是健康管理闭环的服务对象底座。
- 患者管理横跨 B 端患者池、C 端用户注册、院内 API 数据拉取和患者档案。
- 患者管理涉及租户 / 科室归属、档案匹配、团队分配和在管关系。
- 患者管理依赖健康数据中心，并支撑后续方案、任务和预警。

#### 2.2.2 业务背景知识

- 当前统一称为患者，特殊预警等场景可按业务语境转换称呼。
- 当前没有明确“目标人群”概念，也没有明确筛选识别流程，该部分先挂起。
- 患者管理以患者进入统一患者池为起点。
- 患者对应一个自然人，患者和患者档案是一对一关系。
- 用户是系统语境用词，主要指 C 端注册形成的账号主体。
- 一个 C 端用户可关联多个患者档案，用于家庭式管理。
- 患者主要有两个入口：院内 API 拉取和 C 端注册。
- 院内 API 拉取来的患者信息能满足业务需求。
- 不同租户的数据要求不同，不适合用统一标准评价患者信息是否完整。
- C 端注册先形成用户，用户建档后才进入档案体系。
- 院内 API 拉取和 C 端注册两种方式进入的患者都会进入统一患者池。
- 档案记录统一管理，进入时先查库，已有则匹配，无则新增。
- 档案匹配校验规则参考健康数据中心文档。
- 院内 API 拉取来的患者即使没有 C 端用户，也可以被 B 端管理。
- 患者会有机构归属，即租户，同时会带科室信息。
- 患者进入患者池并具备租户、科室归属，不等于进入在管状态。
- 是否要管是另一层业务，需要后续团队分配或服务动作承接。

#### 2.2.3 系统功能改造

- 需要承载统一患者池。
- 需要明确用户 / 患者 / 档案关系。
- 需要支持档案查重、匹配和新增。
- 需要支持租户 / 科室归属。
- 需要区分患者池关系和在管关系。
- 需要与健康数据中心协同身份匹配和数据归属。
- 院内 API 拉取和 C 端注册都需要进入统一患者池。
- 档案进入时需要先查库，已有则匹配，无则新增。
- 一个 C 端用户需要支持关联多个患者档案。
- 院内 API 拉取来的患者需要支持不依赖 C 端用户被 B 端管理。
- 患者进入患者池不应自动成为在管患者。
- 建档问题会影响档案一致性、身份匹配、归属关系、健康数据归属、任务下发、预警触达和团队分配。

#### 2.2.4 待明确问题

- 团队分配 / 在管关系需要进一步确认。
- 患者池列表与患者详情需要进一步确认。
- 档案修改与更正需要进一步确认。
- C 端家庭式管理需要进一步确认。
- C 端建档体验需要进一步确认。
- 数据权限需要进一步确认。

### 2.3 组织管理专题

#### 2.3.1 模块总览

- 组织管理是患者管理、团队分配、在管关系、任务执行、预警处理和数据权限的基础模块。
- 组织管理不是单纯的机构 / 科室 / 人员后台维护页面。
- 组织管理决定患者、人员、数据、任务、预警的归属和权限边界。
- 组织管理涉及机构、院区、科室、团队、人员、角色权限。
- 组织管理当前最大的业务问题是：系统难以兼容实际业务中的复杂情况。
- 本专题保留模块总览，再按子模块拆分梳理。

#### 2.3.2 机构管理

##### 已确认业务背景

- 机构在实际中可为医院、医疗机构、健康管理机构等，在系统中一个机构即一个租户。
- 机构影响患者归属、人员归属、数据归属、数据权限、资源配置和 C 端入口，患者、B 端人员、健康数据都必须归属于机构。
- 现有系统实际是租户对齐院区层级，目标关系需要调整为机构对齐租户，院区作为机构下级层级。
- 集团、区域性组织、医联体等属于租户上级层级，可管理关联多个机构，只做数据查询、统计和管理关联，不参与实际业务执行。
- 一个机构对应一个小程序，即一个 C 端入口，不存在多机构共用小程序或一机构多小程序。
- M 端已有基础租户信息管理功能，当前主要包含名称、key、开通的功能模块等简单信息，不包含系统配置。
- 后续机构管理会增加系统配置能力。
- 机构信息会被平台、机构管理者、B 端人员和 C 端入口等页面展示使用。
- 机构之间允许数据共享，是否共享主要由业务侧决策。
- 暂时不考虑跨机构协作、跨机构查看和平台代运营查看，未来不排除支持。

##### 对系统的影响

- 机构必须作为患者、人员、健康数据和配置的核心业务归属边界。
- 机构边界会影响组织隔离和数据隔离。
- 机构与 C 端入口的关系会影响用户进入和服务归属。
- 租户上级层级需要存在，但不能影响机构内业务执行。
- 现有租户对齐院区会导致机构、院区、科室层级关系错位。
- 现有租户对齐院区会影响患者、人员、数据和 C 端入口的归属判断。
- 机构数据隔离不能假设为绝对隔离。
- 数据共享需要由业务规则控制。
- 机构信息需要满足多端展示和业务识别。

##### 功能改造项

| 功能点 | 改造内容 | 优先级 | 为什么需要 |
| --- | --- | --- | --- |
| 租户层级重构 | 将现有“租户对齐院区”调整为“机构对齐租户”。 | 高 | 机构才是业务执行边界，现有租户层级承载错位。 |
| 租户层级重构 | 将院区调整为机构下级层级。 | 高 | 院区不应继续承载机构边界，需要回到组织层级内部。 |
| 租户层级重构 | 明确患者、B 端人员、健康数据和资源配置都归属于机构。 | 待确认 | 层级重构会影响数据归属、权限判断和后续业务执行。 |
| 机构信息管理 | 完善机构展示信息、key、开通模块等基础字段。 | 低 | 当前 M 端只有简单机构信息，且机构信息会被多端页面展示使用。 |
| C 端入口绑定 | 明确机构与小程序入口的一对一绑定关系。 | 待确认 | 一个机构对应一个小程序入口，用户进入后需要确定服务归属。 |
| 租户上级层级 | 增加租户上级层级模型，支持集团、区域性组织、医联体关联多个机构。 | 待确认 | 上级层级需要做查询、统计和管理关联，但不参与机构内业务执行。 |
| 机构间数据共享 | 增加机构间数据共享规则能力。 | 待确认 | 机构之间允许数据共享，是否共享由业务侧决策。 |

##### 待确认问题

- 租户上级层级的数据模型需要进一步确认。
- 租户上级层级的查询和统计范围需要进一步确认。
- 机构级系统配置范围需要进一步确认。
- 机构间数据共享的业务规则需要进一步确认。
- 未来是否支持跨机构协作、跨机构查看和平台代运营查看需要后续确认。

#### 2.3.3 院区管理

##### 已确认业务背景

- 标准组织层级可为租户 -> 院区 -> 科室。
- 院区是租户下的可选组织层级。
- 院区位于租户和科室之间。
- 并非所有机构都需要院区。
- 现有系统实际是租户对齐院区层级。
- 当前系统没有院区管理功能。
- 前期可接受院区没有前端管理界面。
- 前期院区只要能在数据库表中写入和管理即可。

##### 对系统的影响

- 组织层级不能写死为固定三层。
- 院区必须作为可选层级被底层数据模型支持。
- 院区不能继续作为租户层级承载机构边界。
- 无院区的机构形态也必须能正常运行。

##### 功能改造项

- 新增院区数据模型，支持院区数据写入和维护。
- 院区前期可不建设前端管理界面。
- 院区数据需要归属于租户。
- 院区数据需要支持后续科室挂接。

##### 待确认问题

- 院区数据表结构需要进一步确认。
- 院区是否参与数据权限控制需要进一步确认。
- 院区是否影响患者归属需要进一步确认。

#### 2.3.4 科室管理

##### 已确认业务背景

- 科室是租户下或院区下的组织层级。
- 并非所有机构都需要科室。
- 患者进入系统后会带科室信息。
- 科室可能影响患者来源、人员归属和数据权限。

##### 对系统的影响

- 科室必须兼容直属租户和归属院区两种情况。
- 无科室的机构形态也必须能正常运行。
- 患者科室信息会影响患者来源、人员协作和数据权限判断。

##### 功能改造项

- 调整科室模型，兼容有院区和无院区两种场景。
- 科室结构需要支撑患者来源记录。
- 科室结构需要支撑人员归属。
- 科室结构需要支撑数据权限规则。

##### 待确认问题

- 科室是否必须归属院区需要进一步确认。
- 科室是否影响人员和数据权限需要进一步确认。
- 患者科室信息的来源和变更规则需要进一步确认。

#### 2.3.5 团队管理

##### 已确认业务背景

- 团队分配是患者进入系统后的后续管理动作。
- 患者进入患者池不等于进入在管状态。
- 团队需要承接患者管理、任务执行和预警处理。

##### 对系统的影响

- 团队分配会决定患者是否进入实际管理关系。
- 团队关系会影响任务承接和预警责任归属。
- 团队调整会影响患者、任务和预警交接。

##### 功能改造项

- 梳理团队模型，支撑患者分配。
- 团队模型需要支撑在管关系。
- 团队模型需要支撑任务承接。
- 团队模型需要支撑预警责任归属。

##### 待确认问题

- 团队如何组成需要进一步确认。
- 团队与科室的关系需要进一步确认。
- 团队如何承接患者和任务需要进一步确认。
- 团队调整时患者、任务和预警如何交接需要进一步确认。

#### 2.3.6 人员管理

##### 已确认业务背景

- 人员主要指 B 端医护、健管师、机构管理者等参与健康管理的人员。
- 人员需要归属于租户。
- 人员可能归属于科室。
- 人员可能归属于一个或多个团队。

##### 对系统的影响

- 人员与机构、科室、团队、角色的关系会影响任务和预警承接。
- 人员变更会影响患者、任务和预警交接。
- 人员组织归属会影响数据权限判断。

##### 功能改造项

- 梳理人员模型，支撑机构、科室、团队、角色关系。
- 人员管理需要支持跨科室、跨团队、离职等变更。
- 人员变更需要联动患者、任务和预警交接。

##### 待确认问题

- 人员是否可跨科室需要进一步确认。
- 人员是否可加入多个团队需要进一步确认。
- 人员离职后的患者和任务交接规则需要进一步确认。

#### 2.3.7 角色权限

##### 已确认业务背景

- 角色权限定义功能权限、职责边界和数据权限规则。
- 患者和档案的可见范围需要基于租户、科室、团队、人员和角色权限确认。
- B 端人员能否查看、操作某个患者，依赖组织与数据权限规则。

##### 对系统的影响

- 角色权限不能只控制菜单，还需要控制数据可见范围。
- 数据权限模型会影响患者和档案的可见范围。
- 功能权限和数据权限可能需要分离配置。

##### 功能改造项

- 梳理角色权限模型，支撑功能权限、操作权限和数据权限。
- 数据权限需要支持租户、科室、团队、本人、全院等范围。

##### 待确认问题

- 角色权限是否支持租户自定义需要进一步确认。
- 数据权限范围模型需要进一步确认。
- 功能权限和数据权限是否分离配置需要进一步确认。

##### B 端主流程

###### 患者进入患者池、建档、导入、同步与身份匹配

| 项目     | 内容                                                                                                                                                                                                                                                                 |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 业务目标   | 让患者通过不同入口进入系统统一患者池，为后续建档、分组、方案、任务、预警和服务闭环提供统一对象。                                                                                                                                                                                                                   |

| 当前现状   | 当前没有目标人群概念，统一称为患者。患者主要有两种进入方式：通过 API 向院内系统拉取患者数据；通过 C 端注册。两种方式进入的患者都会进入系统统一患者池。院内 API 拉取的数据能够满足业务需求，但不同租户的数据要求不同，不适合用同一标准评价“完整”。C 端注册进入的是用户，用户需要建档才有档案概念；档案记录统一管理，无论从哪个方式获得患者档案，都会先查库是否已有对应档案，无则新增，有则匹配，匹配校验规则参考健康数据中心文档。患者会有机构归属，即租户，同时会带科室信息；分配团队是后续动作，需要单独重点梳理。 |
| 问题与缺口  | 当前建档流程经过多次迭代后已经混乱，变得不可维护，需要重新梳理。患者池、用户、档案、租户归属、科室归属、后续团队分配之间的流程边界需要重新明确。                                                                                                                                                                                           |
| 风险点    | 建档流程不可维护会影响患者档案一致性、患者身份匹配、健康数据归属、任务下发、预警触达、团队分配和后续健康管理服务闭环。                                                                                                                                                                                                        |
| 后续清单线索 | 建档流程重梳。                                                                                                                                                                                                                                                            |

# 健康管理方案体系脑暴

## 1. 文档定位

本文是健康管理方案体系重构前的业务脑暴文档。当前阶段抛开既有系统、既有页面和历史实现，只从慢病管理与长期健康管理业务本身出发，建立基础业务理解并形成阶段性结论。

本文第 2 章聚焦业务理解，不讨论页面设计和技术实现；第 3 章进入产品设计层面的方向性讨论，不涉及具体技术实现、接口字段和代码改造。本文重点回答：

- 慢病 / 健康管理业务的本质是什么。
- 真实业务中一般如何进行持续健康管理。
- 业务中有哪些稳定角色、对象、动作、数据和闭环。
- 后续设计健康管理方案体系时，应以什么业务原点作为判断依据。

说明：本文为业务脑暴文档，保留任务、打卡、随访、阶段评估等真实业务动作表述。后续正式方案体系设计中，配置层统一以 V3.0 中的“管理路径节点”为核心口径；任务、打卡、随访、宣教、复诊、评估等可作为路径节点的节点类型、执行表现或执行记录。

## 2. 业务知识板块

### 2.1 业务本质与主线

慢病 / 健康管理不是一次性诊疗，也不是单次报告交付，而是一套围绕特定人群持续运行的服务管理过程。

它的核心是：

```text
识别需要管理的人
-> 判断当前健康状态和风险
-> 设定阶段性管理目标
-> 安排患者和医护要执行的动作
-> 持续采集数据和反馈
-> 发现异常并干预
-> 周期性评估效果
-> 决定继续、调整、升级干预或结束
```

因此，慢病 / 健康管理本质上是长期服务闭环，不是内容生成，不是任务下发，也不是单纯健康档案展示。

健康管理方案不应被理解为一份静态文档。它更像是一个服务执行框架，负责回答：

```text
管谁？
为什么管？
当前状态如何？
这一阶段要达成什么？
患者要做什么？
医护要做什么？
系统要监测什么？
异常时怎么处理？
阶段结束如何评估？
下一步如何调整？
```

一份完整健康管理方案至少应包含：

```text
管理主题
适用对象
基线评估
管理目标
监测数据
管理路径节点
预警规则
阶段评估
调整规则
```

### 2.2 核心对象及其关系

这些对象之间的初步关系可以表达为：

```text
患者
-> 有健康档案
-> 被纳入某个管理主题
-> 形成一份管理方案
-> 方案围绕目标、监测数据、管理路径节点、预警干预和评估决策组织
-> 执行过程产生数据、记录和事件
-> 阶段评估汇总结果
-> 形成下一步管理决策
```

需要特别区分：

```text
监测数据 = 被持续观察的结果
打卡 = 患者形成记录的动作入口
任务 = 要完成的服务动作
预警 = 对异常状态的识别和处理入口
评估 = 对一段管理周期的复盘
```

这几个对象不能混成同一个概念。在正式配置口径中，任务、打卡、随访、复诊和评估不作为彼此并列的上层配置对象，而是统一由管理路径节点承载；节点执行后再形成对应的任务记录、打卡记录、随访记录、复查结果或评估结果。

### 2.3 业务闭环、异常与评估

患者侧常见动作包括：

```text
测量血压 / 血糖 / 体重
记录饮食、运动、睡眠、用药
完成问卷或量表
阅读宣教内容
执行复查或门诊复诊
反馈症状或不适
查看阶段建议
```

医护侧常见动作包括：

```text
建档
评估风险
制定或确认方案
下发任务
查看监测趋势
查看患者打卡和依从性
随访
处理异常
调整目标或任务
生成阶段总结
判断是否转诊或结营
```

系统侧常见动作包括：

```text
同步健康数据
整理指标趋势
提醒患者执行任务
提醒医护跟进异常
识别未打卡、超阈值、路径节点逾期
生成摘要或评估建议
归档服务过程
```

三方动作在配置层统一映射为管理路径节点，具体映射关系见 2.2 节。

慢病管理不能只下发任务。真正有价值的问题是：

```text
路径节点是否执行？
执行后产生什么数据？
数据是否达标？
患者是否持续参与？
是否出现异常？
医护是否处理？
处理后是否改善？
下一阶段是否需要调整？
```

因此，路径节点配置只是起点，执行反馈、数据变化、医护干预和阶段评估共同构成闭环。

常见异常包括：

```text
血压 / 血糖 / 体重等指标超过阈值
连续未完成打卡类节点
路径节点逾期未完成
患者反馈不适症状
用药依从性差
复查未完成
指标长期不改善
短期趋势快速恶化
患者失联
```

异常之后不能只做提示，而应连接处理动作：

```text
提醒患者
通知医护
生成随访节点或临时处置动作
要求复测
建议复诊
升级给医生
调整方案
记录处理结果
纳入阶段评估
```

阶段评估是慢病管理从执行走向管理的关键。它回答：

```text
这一阶段有没有效果？
目标是否达成？
指标有没有改善？
患者有没有按要求执行？
发生过哪些异常？
医护是否及时处理？
下一阶段继续原方案，还是调整？
是否需要结营、转诊或升级干预？
```

阶段评估的输入通常包括目标达成情况、指标趋势、打卡完成情况、任务完成情况、随访完成情况、预警发生与处理情况、患者反馈和医护评价。

阶段评估的输出通常包括阶段总结、管理效果判断、调整建议、下一阶段计划，以及结营、续管、转诊或升级干预判断。

在正式配置口径中，阶段评估可以作为管理路径中的评估类节点配置；但其业务作用不同于普通执行节点，重点在于阶段复盘和下一步管理决策。

### 2.4 阶段性业务结论

基于初步调研，当前阶段先形成以下业务结论：

**方案本质**

1. 慢病 / 健康管理的核心对象是”患者在某个健康管理主题下的一段持续管理过程”。
2. 健康管理方案不是静态文档，而是承载目标、监测数据、管理路径节点、预警和评估的执行框架。
3. 健康管理必须区分模板和患者实例：模板负责标准化，实例负责个体化执行。

**路径与闭环**

4. 数据不是附属展示，而是管理过程的判断依据，包括基线、监测、预警和评估。
5. 打卡不是管理路径节点本身，而是患者侧记录、反馈和参与的入口，可作为路径节点的节点类型或执行记录。
6. 路径节点不是闭环本身，节点执行后的数据变化、异常处理和阶段评估才构成闭环。
7. 预警必须连接处理动作，否则只是风险提示。
8. 阶段评估是判断管理是否有效、是否调整方案的关键节点。

**角色与 AI**

9. 医护端关注管理和干预，患者端关注执行和反馈。
10. AI 可以参与摘要、推荐、生成和解释，但关键医学判断必须保留人工确认。

慢病 / 健康管理业务可以先被定义为：

```text
围绕特定健康问题，对患者进行建档、分层、目标设定、管理路径执行、数据监测、异常干预和阶段评估的持续服务闭环。
```

这一定义是后续健康管理方案体系、对象建模和页面设计的业务原点。

## 3. 产品设计板块

### 3.1 创建与编辑模式关键结论

当前产品功能可定义为：AI 原生健康管理方案共创与编排工作台。

它的核心不是让用户填写方案配置表单，也不是让 AI 生成一段方案文本，而是让用户、AI 和多专业智能体围绕一份结构化方案草案进行持续共创和编排，最终形成可发布、可执行、可追踪、可评估的健康管理方案。

AI 原生不是 AI 化界面，而是意图驱动、生成先行、结构隐形、路径可视、智能校验、人工确认的产品逻辑。

关键结论：

1. 创建与编辑应采用 `自然语言意图 + 多智能体共创 + 方案编排 + 局部智能修改 + 人工确认发布` 的模式。

2. AI 和多专业智能体直接参与方案生成。营养、运动、慢病管理、安全校验等智能体应参与对应内容的生成、补全、优化和校验，而不是只在生成后提供意见。

3. AI 生成结果必须落到结构化方案草案。结构化草案用于支撑节点执行、提醒、记录、预警、评估、调整和发布，不能停留在文本方案层。

4. 结构化不等于表单化。结构化配置是系统运行的底层条件，但默认表现层不应直接等同于表单；表单只作为精修、高级配置或校验场景下的补充方式。

5. 默认主体验应围绕管理路径和方案结构编排展开。健康管理方案不是一篇文章，也不是一组字段，而是一条会运行的管理路径，因此界面应优先呈现方案对象、路径节点、重复规则、时间锚点、预警触发和阶段评估。

6. 用户的主要操作不是填字段，而是提出意图、选择对象、调整节点、补充约束、采纳建议、确认变更和发布方案。

7. 局部智能修改应成为核心能力。用户选中某个对象或节点后，可以用自然语言提出调整，AI 自动映射到底层结构并重算相关内容。

8. AI 修改必须形成确认闭环。系统应明确修改对象、修改内容、影响范围和待确认项，再由用户确认是否应用。

9. 文档式表达和结构视图都应作为辅助视图。文档式表达用于说明方案意图、适用对象、专业建议和整体摘要；结构视图用于精细配置和校验，但二者都不应成为唯一主界面。

核心提炼：创建编辑模式的关键不是把传统配置表单 AI 化，而是让用户、AI 和多专业智能体围绕结构化方案草案持续共创，并完成管理路径和方案结构的编排。

### 3.2 产品设计目标

建设一个 AI 原生健康管理方案共创与编排工作台。

它不是传统“方案配置后台”，也不是简单“AI 聊天生成方案”，而是以 AI 和多专业智能体为核心生产力，将健康管理方案从自然语言意图输入、专业内容生成、结构化路径编排、局部智能修改到人工确认发布，贯穿为一套完整产品流程。

核心目标：

1. 以自然语言启动方案创建。

用户不从字段和菜单开始，而是通过描述管理主题、人群、周期、目标和约束，让 AI 生成结构化方案草案。

2. 以多专业智能体参与方案共创。

将营养、运动、慢病管理、安全校验等专业角色能力抽象为智能体，直接参与方案内容生成、补全、优化和校验。

3. 以结构化方案草案承载生成结果。

AI 输出不是纯文本，而是可编辑、可校验、可发布、可执行的结构化方案草案，包括基础信息、监测数据、管理路径节点、预警规则、评估和调整规则。

4. 以编排面承载方案结构。

编排面承载基础信息、监测数据、管理路径、预警规则等核心对象，支持查看、定位、调整和编排。编排面的具体视觉形态（画布、列表或其他形式）在 3.5 节中讨论。

5. 以管理路径为核心编排对象。

重点配置路径节点、时间锚点、重复规则、执行对象、节点类型、触发逻辑和阶段评估安排。

6. 以局部智能修改持续完善方案。

用户可选中对象或节点，用自然语言提出调整，AI 自动映射到底层结构，并联动重算相关节点、提醒、评估和预警逻辑。

7. 以发布前校验保障可执行性。

系统应校验方案完整性、节点时间规则、重复规则冲突、预警处理动作、高风险内容和人工确认边界。

8. 以人工确认守住专业责任边界。

AI 和智能体负责生成、补全、优化和校验，最终医学判断、高风险内容、发布动作必须保留人工确认。

一句话目标：

打造一个由用户意图驱动、多专业智能体共同生成、在编排面上调整结构化方案，并通过局部智能修改持续完善的健康管理方案共创与编排工作台。

### 3.3 整体交互设计方案

当前阶段，产品形态的探索方向为：AI 原生健康管理方案共创与编排工作台。

探索中的核心布局为三栏结构（此布局为当前假设，3.5 和 3.6 节对其进行了进一步审视）：

```text
左侧结构索引
中央编排面（当前以画布形式探索）
右侧 AI 共创操作台
```

左侧结构索引用于快速定位方案配置对象，只承担轻量导航和对象定位，不承载复杂编辑。

```text
基础信息
监测数据
管理路径
预警规则
```

中央编排面用于承载方案结构本体，展示方案核心对象、管理路径节点、时间锚点、重复规则和状态。编排面应支持拖动、缩放、定位和聚焦。编排面中的配置内容以对象摘要、节点关系和状态为主，不应退化为大表单堆叠。编排面的具体视觉形态（自由画布、结构化列表或其他形式）在 3.5 节中讨论。

右侧 AI 共创操作台用于意图输入、智能体协作、局部修改、生成结果预览、结构化变更确认和发布前校验。AI 对方案的修改不能直接隐式生效，而应让用户看到修改对象、修改内容、影响范围和待确认项。

关键交互闭环：

```text
用户输入管理意图
-> 多专业智能体参与生成
-> 系统生成结构化方案草案
-> 编排面呈现方案结构
-> 用户选中对象或节点提出局部修改
-> AI 重算相关结构并生成变更预览
-> 用户确认后更新方案草案
-> 发布前校验
-> 发布方案
```

多专业智能体不应只是角色展示，而应参与具体方案对象的生成和调整。例如营养智能体生成饮食干预、营养处方和饮食记录要求；运动智能体生成运动节点、频次和强度；慢病管理智能体生成监测数据、阶段评估和预警逻辑；安全智能体负责禁忌、阈值和风险冲突校验。

该设计的核心原则：

1. 左侧负责找对象。

2. 中央负责编排方案结构。

3. 右侧负责 AI 共创、局部修改和发布前校验。

4. AI 生成必须结构化、可调整、可校验、可确认。

5. 结构化配置存在于底层，但默认不以传统表单作为主体验。

一句话定义：

这是一个以自然语言启动创建、以多专业智能体共同生成内容、以编排面承载结构化方案，并通过局部智能修改持续完善的健康管理方案共创与编排工作台。

### 3.4 核心配置对象

在产品配置层，健康管理方案不应直接以任务、打卡、问卷、宣教、处方、随访等具体功能对象作为最高层配置对象，而应先抽象为围绕管理路径运行的一组核心配置对象。

当前阶段，核心配置对象可先收敛为：

```text
管理路径
-> 路径节点
-> 节点时间规则
-> 节点执行内容
```

#### 3.4.1 管理路径

管理路径是一条有时间性的方案执行计划，用于回答：

```text
从管理开始后，什么时间做什么事。
```

管理路径不直接配置具体日期，而是以管理开始时间作为锚点，通过相对时间规则推导具体执行安排。

管理路径建议包含：

- 管理周期
- 管理开始时间锚点
- 路径节点集合
- 节点排序 / 分组
- 是否支持重复节点
- 是否支持条件触发节点

#### 3.4.2 路径节点

路径节点是管理路径中的最小编排单元。

路径节点在配置层不预先绑定为任务、打卡、问卷、宣教、处方或随访等具体功能对象，而是先作为一个“管理动作单元”存在。

路径节点建议包含：

- 节点名称
- 节点类型
- 业务方向
- 时间规则
- 执行内容

其中，节点类型用于表达动作形态，例如宣教、问卷、打卡、处方、复诊、随访、提醒、评估等；业务方向用于表达干预主题，例如饮食、运动、用药、睡眠、营养、慢病管理等。

在执行层，系统再根据节点配置生成患者待办、医护待办、系统提醒、打卡记录、问卷记录、随访记录、评估结果或其他执行记录。

#### 3.4.3 节点时间规则

节点时间规则用于描述路径节点什么时候发生、是否重复、如何展开。

它是管理路径编排中最关键的配置对象之一。

节点时间规则建议包含：

- 时间锚点：通常为管理开始时间
- 发生时间：第几天、第几周、某阶段
- 执行方式：一次性、重复执行、条件触发
- 重复频率：每日、每周、每月或自定义
- 重复范围：例如第 1-90 天、某阶段内
- 例外规则：例如周末不执行、节假日跳过
- 结束条件：周期结束、目标达成、人工停止等

例如：

```text
第 1-90 天，每周 5 天执行饮食记录，周末不提醒。
```

该场景在配置层应被理解为一个路径节点加一组重复规则，而不是配置或生成 90 个独立任务。

#### 3.4.4 节点执行内容

节点执行内容用于描述路径节点具体要完成什么。

节点执行内容可以是：

- 宣教材料
- 问卷表单
- 打卡要求
- 运动建议
- 营养处方
- 随访要求
- 评估指标
- 异常处理说明

节点执行内容可以在后续功能设计中继续细分，但在当前阶段不宜过早拆成功能模块。

#### 小结

管理路径编排的核心，不是配置任务，而是配置一组带时间规则和执行内容的路径节点。

任务、打卡、问卷、宣教、处方、随访等具体功能对象，不应作为管理路径配置的上层对象，而应作为路径节点在执行层的表现形式或执行记录。

### 3.5 管理路径配置思路

#### 3.5.1 管理路径编排的本质需求

在设计具体编排方式之前，需要先明确用户编排管理路径时实际执行哪些操作。当前阶段将编排动作归纳为两类：

**逐节点操作（高频）**

- 添加节点：在路径中新增一个节点，指定类型、方向和内容
- 调整时间：修改节点的起始时间、结束条件或重复规则
- 修改属性：调整节点的执行对象、执行内容、提醒规则
- 调整顺序：改变节点在路径中的先后位置
- 删除或禁用节点：移除或暂停某个节点

**全局扫描（间歇性）**

- 检查空档：管理周期内是否存在长时间没有任何节点的空白期
- 检查密度：某个时段节点是否过密，是否超出患者执行能力
- 检查覆盖：评估节点是否在合适的时间点触发，预警规则是否覆盖全周期

两类操作的频次和使用方式不同：逐节点操作是编排的主行为，约占大部分交互量，需要快速、精确、低摩擦；全局扫描是间歇性的判断动作，需要一目了然，但不承载精细编辑。

任何编排方式的设计都应符合这个频次分布——为高频操作优化的主界面，加上需要时触达的全局概览，而非反过来。

#### 3.5.2 探索方向一：时间轴 / 甘特图

中央自由画布的具体视觉范式尚在探索阶段，本节将时间轴（甘特图形式）作为一个重点方向进行讨论，尚未确定为最终方案。画布的最终视觉范式需要在原型验证和用户反馈后收敛。

**探索依据：管理路径的数据本质**

管理路径节点天然是时间序列数据——每个节点包含何时开始、持续多久、是否重复三个时间维度。一个方案中多个节点在时间轴上并行铺开：饮食打卡和运动打卡同时运行，随访穿插其中，评估在特定节点触发。这本质上是一套「多轨道、有时间跨度、有里程碑」的并行时间序列。

画布的视觉范式需要匹配这一数据本质。时间轴/甘特图是展示并行时间序列最成熟的视觉范式之一——横轴为时间，纵轴为节点轨道，条块长度表达持续时间，菱形标记表达评估里程碑。项目管理领域使用甘特图看项目如何运行，与健康管理领域看方案如何运行的认知需求有相通之处，因此将其作为优先探索方向。

**与其他可能的视觉范式的对比**

以下为当前阶段对几种候选范式的初步分析，不构成最终结论：

| 范式      | 潜在优势            | 在管理路径场景下的已知问题                |
| ------- | --------------- | ---------------------------- |
| 卡片堆叠    | 对象摘要直观，学习成本低    | 并行关系不可见，持续时间不可比，时间间距不可感      |
| 日历视图    | 精确日期排期，时间感准确    | 重复节点（每日 ×90）会撑爆日历，结构层次丢失     |
| 流程图     | 适合展示串行依赖        | 管理路径节点多为并行独立运行，流程图的串行假设不完全匹配 |
| 时间轴/甘特图 | 时间关系一目了然，并行状态清晰 | 字段级精修不便，节点数量多时密度高，移动端适配困难    |

以上范式的对比需要在原型中实际验证，不同场景可能需要不同范式或组合使用。

**若采用时间轴范式，与文档视图、结构视图的关系**

假设时间轴方向通过验证，它将是默认的主视图，但不是唯一视图。三种视图分别服务于不同认知需求：

- **路径视图（如时间轴）**：回答「方案如何运行」——时间关系、并行状态、里程碑位置。
- **文档视图**：回答「方案说了什么」——意图说明、专业建议、整体摘要。用于阅读理解和对外沟通。
- **结构视图**：回答「方案配了什么」——字段级完整配置、校验结果。用于精修和发布前核查。

无论编排面最终采用哪种视觉范式，三种视图应在统一入口中提供切换，切换时保持选中对象不变。结构在呈现层的角色详见 3.6.5 节。

**时间轴范式的已知局限**

即使时间轴方向可行，以下场景也不应由时间轴单独承载：

- 单个节点的字段级精修 → 更适合结构视图或侧边抽屉面板
- 患者端今日待办 → 更适合卡片/清单，时间轴过于宏观
- 实例执行进度追踪 → 需要在时间轴上叠加执行状态和进度层，具体方案在实例执行相关章节单独讨论
- 移动端或窄屏环境 → 横向时间轴在小屏上操作不便，需要不同的布局策略

这些场景需要通过视图切换或辅助交互承载，而非在主画布中解决。具体范式的选择和组合方式，应通过原型验证和用户测试进一步收敛。

**对时间轴范式的进一步审视**

时间轴范式的舒适区是全局扫描：一眼看清节点在时间上的分布、并行关系和里程碑位置。但逐节点操作在时间轴上并不高效——在横向拉伸的长画布上定位一个节点、修改其属性、调整其时间，每一步都伴随着缩放、平移和视线跳跃。

缩放控件、概览条、视口导航、纵向降级等方案，本质上是为同一个问题打补丁：时间轴的主交互面积太大，而大部分操作只需要针对单个节点。当大部分操作是逐节点的，主界面却为间歇性的全局扫描需求分配了全部空间，比例失衡。

这不是时间轴实现得不够好，而是它的核心能力（全局时间可视化）与编排的主行为（逐节点操作）之间存在结构性错配。时间轴作为编排主界面可能不是最优解，但其全局时间概览能力有独特价值——问题不在于时间轴本身，而在于不应把它放在主界面的位置。

#### 3.5.3 探索方向二：结构化列表 + 时间概览

**基本思路**

将管理路径编排的主界面设计为一个带有时间感知的结构化列表，而非需要导航的自由画布。

列表的每一行对应一个路径节点。行按时间顺序排列——第 1 天的节点在第 14 天的节点上方，时间关系由排序本身表达，不依赖横向坐标轴。每行包含节点名称、类型、方向、时间描述等关键信息，并附带一个紧凑的微型时间指示（sparkline），用于区分单次节点、持续节点和重复节点，提供时间属性的快速视觉线索但不承载精确的全局坐标。

列表顶部提供一个可折叠的全局概览条（约 80px 高），以周为单位压缩展示整个管理周期内的节点分布密度和里程碑位置。概览条只读、不可交互，用于「修改后看一眼有没有空档和密集区」——需要时展开，看完收起。

**逐节点操作在列表中的交互**

- 添加节点：列表底部新增按钮或在指定位置插入
- 调整时间：行内编辑时间规则，或拖拽行改变顺序
- 修改属性：点击行展开详情面板或在右侧操作台中进行编辑
- 删除节点：行内删除操作
- 全局检查：展开概览条，扫描密度和空档

所有逐节点操作在主界面内完成，无需缩放、平移或画布导航。

**与时间轴范式的关系**

两种范式的取舍本质上是频次匹配问题：

|         | 时间轴/甘特图     | 结构化列表 + 概览           |
| ------- | ----------- | -------------------- |
| 主界面     | 全局时间画布      | 节点列表                 |
| 逐节点操作   | 需要缩放定位，摩擦较高 | 行内操作，直接快速            |
| 全局扫描    | 天然优势，时间关系直观 | 依赖概览条，精度降低但足够判断空档和密度 |
| 适合的频次分布 | 全局扫描为主、编辑为辅 | 逐节点编辑为主、扫描为辅         |

当前阶段的判断是：管理路径编排的主行为是逐节点操作，因此列表模式在频次匹配上更合理。时间轴的能力不丢弃，而是收敛为概览条中的压缩视图——它仍然是全局扫描的最佳工具，只是不再作为主界面。

**对原有设想的重新审视**

3.3 节提出以「自由画布」作为中央编排面，并设想画布应支持拖动、缩放、定位和聚焦。结合以上分析，这一设想可能需要调整：

- 「自由画布」概念可能过度设计了编排交互。编排的本质是逐节点操作辅以全局检查，画布的无限空间和自由导航能力超出了实际需求，反而增加了操作摩擦。
- 中央编排面更可能是「结构化列表 + 可折叠概览条」，而非自由画布。列表本身就是编排面，概览条承担全局扫描。
- 三视图体系中，路径视图 = 列表 + 概览条（编排与扫描一体）；文档视图和结构视图的定位不变。
- 甘特图/时间轴的价值回流到概览条——它是一个压缩的、只读的全局视图，服务于间歇性的检查判断，而非持续的编排操作。

这一方向尚未经过原型验证，与时间轴范式一样处于探索阶段，最终编排方式应在原型对比和用户测试后收敛。

### 3.6 AI 原生编排范式的再审视

3.5 节围绕管理路径的具体编排方式进行了探索和对比。但在此之前，有一个更根本的问题需要审视：当前整体设计方案中，结构化配置的权重是否过高，以至于偏离了 AI 原生的产品定位。

#### 3.6.1 结构化配置对 AI 的潜在限制

当前方案中，路径节点的结构化字段——节点类型（打卡/问卷/随访/评估）、业务方向（营养/运动/用药）、时间规则（第 N 天、重复频率）、执行内容——为系统执行提供了确定性。但需要区分：这些字段是为系统运行服务的，而不是为用户认知服务的。

用户的真实思考方式不按这些字段展开：

> 「患者前两周要适应饮食记录，第三周开始加运动，一个月时随访看看效果，血糖如果控制不好要及时干预。」

这句话里没有「节点类型」「业务方向」「时间规则」这些分类。用户脑中是一个完整的时间叙事，动作、条件、对象自然交织。

当前模式是「人定义 schema → AI 按 schema 填空 → 人校验 AI 填的对不对」。这个模式下，schema 给了 AI 明确的边界，但也带来了限制：

- AI 只能填充已有字段，无法创造新的字段类型。如果某个管理场景需要一个未定义的结构（例如「术后康复需要记录引流管拔除时间」），AI 无处安放这个信息，用户也看不到。
- AI 的领域判断被 schema 框住。模型底层有大量临床知识——它可能知道糖尿病人应监测足部状况，但 schema 没有「足部检查」这个节点类型，它就提不出来。或者提出了，但因为没有对应的结构槽位，只能以备注形式存放，丢失了可执行性。
- 用户看到的是 schema 的投影，不是 AI 的全部输出。AI 生成了一段完整的方案推理，落到界面上被肢解为若干模块和字段，推理过程和上下文丢失。

这不是结构化本身的问题——结构化对系统执行是必要的。问题在于：**结构化是否应该作为用户与 AI 之间的主要交互界面。** 当结构化字段成为界面的主角，AI 的能力被压缩为一个「智能填表器」，而非一个真正的共创伙伴。

#### 3.6.2 路径编排的本质回归

如果暂时忘掉所有结构化字段和界面约束，路径编排的本质可以回到最原点：

> 一个人在描述他想要的健康管理过程。他希望这个过程被理解、被确认、然后被执行。

这个过程仅包含三个基本要素：

- **什么时间**（时序）
- **发生什么**（事件）
- **谁来做**（角色）

其他一切——节点类型、业务方向、重复规则、执行内容、预警条件——都是这三个要素在不同维度上的派生。它们是执行层需要的标签和参数，但不是用户在描述过程中使用的认知单元。

用户不需要看到「打卡」「问卷」「随访」这些分类。它们可以由 AI 在理解用户意图后，在后台自行判断和映射，在必要时向用户确认。用户的交互对象是一段连贯的意图描述，不是一个结构化表单。

#### 3.6.3 AI 原生编排的交互设想

基于以上分析，AI 原生的路径编排可以不采用「结构化编辑面板 + AI 辅助面板」的双轨模式，而是以对话为唯一的交互主轴：

- 用户在对话中描述管理意图，AI 理解并生成方案推理
- AI 的回复同时包含自然语言解释和底层结构化方案的同步更新
- 用户通过对话持续调整——「饮食记录改成每天 1 次」「第 14 天加一次随访」——每次调整即时反映到方案中
- 关键医学判断（阈值、高风险内容）AI 主动提问确认，用户作答
- 结构不是消失了，而是退到对话的幕后。需要时（如发布前）可调出查验，不需要时不占据界面

在这个设想下，整个交互模式从「在结构中填内容」转变为「在对话中做决策」，AI 从辅助面板进入主引擎位置。

需要区分的是：对话驱动编排与简单的 AI 聊天有本质区别。AI 聊天的输出是纯文本，对话结束后用户需要自行理解和执行；对话驱动编排的每一次交互都在更新底层结构化方案草案——用户说「第 14 天加一次随访」，系统不只是回复文本，而是在方案结构中新增一个随访节点，同步更新执行时间、医护待办和评估关联。对话是交互方式，结构化方案是产出物。这与 3.2 中「不是简单 AI 聊天生成方案」的定位一致——对话是手段，可执行的方案是目的。

同时需要说明的是：这并不意味着抛弃结构化配置。结构化配置作为底层执行条件仍然存在，由 AI 在对话过程中自动维护。变化的是用户与系统交互的层面——用户面对的是对话和决策，而非字段和表单。

**这确实是矛盾：只要 schema 是固定的，AI 的创造力就被限定了上限。** 对话界面解决的是交互层的问题——让用户不用学 schema。但它解决不了 schema 本身刚性带来的限制——AI 不能创造系统不认识的东西。

真正的突破可能需要 schema 本身是**可扩展的**：AI 可以提议新的节点类型或新的执行内容格式，系统可以动态接纳，而不仅仅是往已有槽位里填值。但这是一个远比 UI 设计更难的工程问题，而且并不是单单解决“管理方案体系”即可，而是整个下游都要起底。

#### 3.6.4 对当前设计设想的重新审视

如果 3.6.3 的方向成立，当前产品设计板块中的几个核心设想可能需要重新讨论：

| 当前设想                       | 需要重新审视的内容                                           | 可能的替代方向                          |
| -------------------------- | --------------------------------------------------- | -------------------------------- |
| 3.3 三栏布局（左索引 / 中画布 / 右 AI） | AI 不再只是右侧操作台——对话应成为中央主交互面。三栏布局是否仍是合适的架构？            | 两栏布局（左索引 + 右对话预览区），AI 对话为主引擎     |
| 3.4 核心配置对象（路径节点、时间规则等）     | 这些对象是执行层的结构，不应成为用户界面的默认呈现。界面上用户看到的是时间叙事，不是字段集合。     | 执行层保留完整结构，表现层以时间叙事和对话反馈呈现，结构按需调出 |
| 3.5 编排方式的探索（时间轴 vs 列表）     | 两者仍是「以结构为中心的编辑」思路。如果编排发生在对话中，「编辑面」本身的概念可能需要弱化。      | 方案预览（只读、实时同步）替代编辑面，编辑操作在对话中完成    |
| 3.1 9 条关键结论                | 总体方向（意图驱动、生成先行、人工确认）仍然成立，但「画布编排」的核心地位可能需要调整为「对话编排」。 | 将「画布编排」修正为「方案编排」，不绑定到特定视觉范式      |

文档自身存在一定张力：前半部分（3.1、3.2）强调意图驱动和 AI 原生，后半部分（3.3、3.4）在设计落地时又回到了传统软件的结构化思维。这一张力需要在后续迭代中收敛——要么承认结构化编辑是务实的过渡方案，要么决心探索对话驱动的编排范式。

#### 3.6.5 收束：结构与表现的分离

经过以上讨论，当前阶段形成一项基础判断——

**结构是必要的，但结构的呈现方式是可以选择的。**

健康管理方案必须落为结构化配置，否则无法支撑节点执行、提醒、记录、预警、评估和追溯。这一底层约束不会因为交互方式的改变而消失——对话驱动不会消除 schema，只是在用户和 schema 之间加了一层翻译。

因此，真正的问题不是「要不要结构」，而是「结构放在哪一层」：

- **执行层**：结构必须存在，且需要严谨、完整、可校验。这是系统的确定性保障。
- **表现层**：结构不一定可见。用户可以只面对自然语言意图和 AI 反馈，结构在后台由 AI 维护。需要时（如发布前校验、字段精修）可以调出查验，不需要时不占据界面。
- **AI 层**：AI 承担用户意图与结构化配置之间的映射。用户说「两周后随访一次」，AI 将其翻译为：节点类型=随访、时间锚点=管理开始日+14天、执行方式=一次性、执行对象=健康管理师。

这一分层的核心价值在于：它承认了结构的不可消除性，但不让用户为此承担认知代价。用户面对的是决策，系统面对的是结构，AI 是两者之间的桥梁。

**第 3 章阶段结论**

第 3 章产品设计板块经过多轮探索和审视，当前阶段形成以下定论与待决问题：

**已确定的判断：**

1. 健康管理方案的底层必须是结构化配置，这是系统可执行性的保障，不可放弃。
2. 结构化不等于表单化——表现层不应默认以传统表单作为主体验。
3. 管理路径编排的主行为是逐节点操作（增删改调），辅以间歇性的全局扫描。编排工具的设计应符合这一频次分布。
4. 结构放在执行层，表现在 AI 层翻译后呈现给用户，三层分离是 AI 原生编排的基础架构。

**已搁置的方向：**

- 时间轴/甘特图作为编排主界面：其全局可视化能力与编排的高频逐节点操作存在结构性错配。但其压缩概览能力保留为辅助工具（概览条）。
- 纯自由画布作为编排面：画布的无限空间和自由导航超出了编排的实际需求，概念可能过度设计。

**继续探索的方向：**

- 方向 A：结构化编排方案——以结构化列表为编排面，辅以概览条和 AI 辅助面板（在 3.3 三栏架构内优化）。
- 方向 B：对话驱动方案——以对话为交互主轴，AI 承担意图到结构的映射，预览实时同步（可能突破三栏架构）。

两个方向需要在原型对比和用户测试后收敛。以上判断不关闭任何方向的探索空间，仅标注当前阶段的认知边界。

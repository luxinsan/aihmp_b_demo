# 文档撰写全局约束

本文用于约束 `docs/system-rebuild` 目录下系统重构相关产品文档的撰写方式，作为后续功能框架、业务方案、能力方案和调研文档的统一表达基准。

## 1. 文档定位约束

- 文档优先服务于产品、研发、实施和业务对齐，不写成技术实现说明。
- 每份文档必须先说明自身定位、边界、与其他文档或模块的关系。
- 不把多个底座能力强行合并到一个文档中；有关联则说明协同关系和职责边界。
- 文档应沉淀方向、原则、能力、边界和待决策问题，避免只堆菜单或功能点。

## 2. 表达风格约束

- 表述保持严谨、专业、精简、干练。
- 优先使用明确结论、结构化条目和稳定业务对象名称。
- 分端命名统一遵守根目录 `TERMINOLOGY.md`：B 端表达为医护端，C 端表达为患者端或客户端，M 端表达为平台管理端。
- 避免口语化、营销化、泛泛形容和重复解释。
- 避免未经确认的绝对化判断；不确定内容标记为“待确认”“方向性判断”“一期建议”。
- 尽量用能力、对象、流程、边界、规则组织内容，而不是只写页面功能。

## 3. 产品逻辑约束

- 先定义业务对象，再定义功能能力。
- 先说明业务场景，再说明系统能力。
- 先区分资源、执行、结果、数据治理，再讨论页面和操作。
- 对核心对象必须说明：是什么、由谁创建、被谁引用、生命周期、与其他对象关系。
- 对跨模块能力必须说明职责边界，避免职责混杂。

## 4. 功能规划约束

- 功能框架要区分一期、二期、后续扩展。
- 一期优先建立稳定模型和闭环，不追求复杂能力一次到位。
- AI、语音、自动化能力可以规划目标态，但要标明建设阶段和安全边界。
- 涉及医学判断、量表解释、风险提示时，要强调专业审核、解释依据和适用范围。
- 涉及平台级资源与租户自建资源时，要明确治理边界。

## 5. 推荐文档结构

后续产品方案可默认采用以下结构：

1. 文档定位
2. 背景与目标
3. 核心原则
4. 产品定位
5. 核心业务对象
6. 应用场景
7. 能力框架
8. 关键流程
9. 与相关模块关系
10. 建设优先级
11. 待确认问题

# 健康管理方案体系 V3.0

## 1. 文档目的

本文定位为健康管理方案体系的业务框架说明文档，用于定义系统中健康管理方案的核心概念、内容框架和模块关系，为后续健康管理方案相关功能设计提供统一业务依据。

本文重点回答以下问题：

- 什么是健康管理方案。
- 健康管理方案、方案模板和患者健康计划实例之间的基本关系。
- 一份慢病或长期健康管理方案应包含哪些核心内容。
- 监测数据、管理路径节点、预警干预、阶段评估等能力如何围绕健康管理主题组织。
- 后续系统建设应如何兼顾标准化配置与患者个体化执行。

本文不展开具体页面交互和技术实现。

## 2. 概念定义

健康管理方案体系不应被理解为单一的“计划编辑器”或“任务配置工具”，而应被定义为：围绕特定健康管理主题，将管理目标、监测数据、管理路径节点、预警干预、阶段评估和调整退出规则组织起来的一套服务执行框架。

- **健康管理主题**：
  
  - 健康管理主题是方案设计的上层业务分类，用于定义某一类健康问题或管理场景的标准管理框架。
  
  - 健康管理主题决定该类方案通常需要关注哪些指标、设置哪些目标、配置哪些管理路径节点、触发哪些预警干预以及如何做阶段评估。
  
  - 示例：高血压管理；2 型糖尿病管理；体重管理 等

- **健康管理方案模板**：
  
  - 方案模板是围绕健康管理主题配置的一套可复用标准方案。
  
  - 模板本身不直接代表某个患者正在执行的计划。
  
  - 模板用于提高建方案效率，适合沉淀机构、科室或服务团队的标准管理路径。
  
  - 例如“高血压 90 天管理模板”“体重管理 28 天干预模板”“糖尿病基础管理模板”等。

- **患者健康计划实例**：
  
  - 患者健康计划实例是将方案模板应用到某个患者后形成的个人健康管理计划，也可以由医护人员直接为患者创建。
  
  - 模板负责标准化，实例负责个体化执行。
  
  - 实例可以来源于模板，但生成后应与模板解耦：
    
    - 修改患者实例，不影响模板。
    
    - 修改模板，不影响已生成实例。
    
    - 实例保留创建时的模板快照和来源信息，用于追溯。
    
    - 实例允许根据患者情况做个性化调整。

- **方案文档：**
  
  - 在部分业务场景中，“健康管理方案”也可能指一份正式交付给客户或患者的文档，例如年度健康管理建议书、90 天健康管理方案建议等。
  
  - 这类内容更适合称为“方案文档”。方案文档偏向分析、建议和交付表达，而系统中的健康计划实例偏向执行和跟踪。

## 3. 健康管理方案的内容框架

结合慢病管理、团队照护、自我管理和国内基本公共卫生服务规范中的常见实践，一份完整的健康管理方案不应只是描述字段集合，而应围绕“适配、目标、执行、监测、异常、评估”组织，形成可配置、可执行、可追踪、可复盘的服务框架。

一份完整的健康管理方案建议包含以下核心内容：

```text
基础信息
-> 管理主题
-> 适用对象
-> 基线评估
-> 管理目标
-> 监测数据
-> 管理路径节点
-> 预警干预
-> 阶段评估
-> 调整与退出规则
```

### 3.1 基本信息

- 基本信息用于定义方案的基础属性，支撑方案管理、检索、发布、引用和追溯。

- 基本信息建议包括方案名称、方案类型、管理周期、适用租户或科室、版本、状态、创建人、更新时间和方案说明等。

- 基本信息不承载具体健康管理逻辑，但应能支撑方案模板的生命周期管理。

### 3.2 管理主题

- 管理主题回答“这份方案主要解决什么健康问题”。

- 管理主题是方案配置的业务入口。主题确定后，系统可以带出该主题下常用的目标、监测数据、管理路径节点、预警干预和阶段评估方式。

- 不同主题可以共享同一套方案框架，但具体指标、路径节点、预警和评估内容应随主题变化。

- 示例：控制血压；改善血糖；降低体重和腰围；改善血脂等。

### 3.3 适用对象

- 适用对象回答“这份方案适合谁”。

- 适用对象可转化为方案匹配条件，用于基于患者全面健康数据进行方案推荐、筛选和适配判断。

- 匹配条件可包括疾病诊断、风险等级、关键指标、年龄范围、生活方式、用药情况、既往病史、服务场景等。

- 方案匹配结果，系统可以给出推荐原因、命中条件和需人工确认的风险点。

### 3.4 基线评估

- 基线评估回答“患者当前处于什么状态”。

- 基线评估用于记录患者进入方案时的初始健康状态，为目标设定、任务安排和阶段评估提供起点参照。

- 基线评估可基于当前可获得的患者数据自动抽取，重点覆盖关键指标、既往病史、当前风险、生活方式和依从性基础。

- 备注：基线评估当前可不作为一期复杂配置项，但患者计划实例启动时应保留必要基线快照。

### 3.5 管理目标

- 管理目标回答“这轮管理要达到什么结果”。

- 健康管理目标不是单纯展示字段，而应成为后续监测数据、管理路径节点、预警干预和阶段评估的依据。

- 目标需可量化、可追踪、可复盘，并能关联到具体监测数据或执行动作。无法追踪和评估的目标，不适合作为方案核心目标。

- 目标可分为指标目标和行为目标。

### 3.6 监测数据

- 监测数据是健康管理方案需要持续关注、引用和评估的数据对象，本身不是执行动作。

- 监测数据用于支撑目标配置、预警干预、趋势分析和阶段评估。行为数据、症状数据和过程数据也属于记录结果，不等同于打卡动作本身。

- 基于数据中心标准数据条目库，统一管理可被方案引用的数据条目。

- 数据条目可与健康管理主题建立关联；当方案主题确定后，系统自动带出推荐监测数据，供方案模板配置和患者计划实例个体化调整。

```text
健康数据条目库
-> 主题推荐条目
-> 方案模板启用与配置
-> 患者计划实例复制与个体化调整
-> 支持预警干预、阶段评估和报告生成
```

### 3.7 管理路径节点

- 管理路径回答“在一个健康管理周期内，什么时间需要做什么管理动作”。

- 管理路径是一条以管理开始时间为锚点的时间性计划。方案模板中不预设具体日期，而是通过相对时间规则定义节点；当患者健康计划实例启动后，系统再根据管理开始时间推导具体执行日期。

- 管理路径由多个路径节点组成。路径节点是健康管理路径中的最小配置单元，用于承载某个时间点、时间段或触发条件下需要执行的管理动作。

- 路径节点在配置层不先绑定为某一种具体业务对象。它可以承载饮食宣教、营养处方、运动要求、用药提醒、问卷、打卡要求、复诊提醒、随访安排、异常处理等内容。

- 在执行层，系统可根据节点配置生成患者待办、医护待办、系统提醒、打卡记录、问卷记录、随访记录或其他执行记录。

一个管理路径节点建议包含：

- 节点名称：用于识别该节点的管理动作。

- 节点类型：宣教、问卷、打卡、处方、复诊、随访、提醒、评估等。

- 业务方向：饮食、运动、用药、睡眠、营养、监测、复查等。

- 节点类型用于定义动作形态，业务方向用于定义干预主题。例如“低盐饮食宣教”的节点类型是宣教，业务方向是饮食；“每日饮食打卡”的节点类型是打卡，业务方向是饮食；“营养处方”的节点类型是处方，业务方向是营养。

- 执行对象：患者、医护、系统，支持多角色协同。

- 时间规则：基于管理开始时间配置相对时间，不配置固定日期。

- 执行内容：该节点具体需要完成的内容或要求。

- 提醒规则：是否提醒、提醒对象、提醒时间、逾期提醒等。

- 完成记录：确认完成、提交数据、上传报告、医护确认或系统自动记录等。

节点时间规则建议包含：

- 时间锚点：管理开始时间。

- 起始偏移：第几天开始，例如第 1 天、第 7 天。

- 执行方式：一次性执行、重复执行或条件触发。

- 重复频率：每日、每周、每月或自定义。

- 执行次数：每日几次、每周几次等。

- 执行时段：早餐、午餐、晚餐、睡前或自定义时间段。

- 结束条件：第几天结束、管理周期结束或满足条件后结束。

其中，阶段评估可作为管理路径中的评估类节点配置。评估类节点回答“这一阶段管理效果如何，下一步怎么办”，可按第 7 天、第 14 天、第 28 天、第 90 天或年度周期等相对时间规则设置，也可由预警事件或关键指标长期未达标等条件触发。

评估类节点的重点包括目标达成、指标趋势、路径节点完成情况、随访完成、预警发生与处理、患者反馈和医护评价。评估结果用于判断是否需要调整目标或计划、进入下一阶段、结营或转诊，并可形成阶段总结、健康管理报告、医护建议和下一阶段计划。

阶段评估在配置层可作为路径节点管理，但其业务作用不同于普通执行节点。普通节点主要推动患者、医护或系统完成具体管理动作；评估类节点用于阶段复盘和下一步管理决策。

示例：

```text
管理开始时间：患者计划实例启动时间

节点 A：第 1 天完成基线问卷
-> 实例启动后，系统推导为启动当天执行

节点 B：管理周期内每日 3 次饮食打卡
-> 模板中只配置 1 个节点
-> 实例启动后，系统按早餐 / 午餐 / 晚餐展开执行安排

节点 C：第 14 天进行阶段随访
-> 系统根据管理开始时间推导第 14 天的随访任务

节点 D：第 28 天进行阶段评估
-> 系统根据管理开始时间推导评估节点
-> 评估结果用于判断是否调整方案或进入下一阶段
```

```text
方案模板
-> 管理路径
-> 路径节点
-> 患者计划实例启动
-> 根据管理开始时间推导具体执行安排
```

### 3.8 预警干预

- 预警是健康管理闭环中的关键机制，用于识别异常状态，并连接后续处理动作。

- 预警不应只是页面提示，而应能触发明确的处理动作，例如提醒患者、通知医护、生成随访任务、建议复诊或升级干预。

- 常见预警类型包括指标异常、症状异常、依从性异常和趋势异常，例如血压或血糖超出阈值、出现胸闷头晕等症状、连续未完成打卡类节点或路径节点逾期、指标长期未达标或波动异常等。

- 预警干预是管理路径执行过程中的异常识别与处置规则。预警可以触发路径节点，也可以生成临时处置动作，例如医护审核、补充随访、复诊建议或升级干预。

- 预警干预应包含：

```text
预警干预
├─ 触发条件
├─ 风险等级
├─ 提醒对象
├─ 处理动作
├─ 是否生成处置动作
├─ 是否需要医护确认
├─ 是否进入阶段评估
└─ 是否需要记录处理结果
```

### 3.9 调整与退出规则

- 调整与退出规则回答“什么情况下需要调整方案、升级干预、转诊、结营或退出管理”。

- 调整规则可基于目标达成情况、监测数据趋势、路径节点执行情况、预警事件、随访反馈和医护判断触发。

- 调整与退出通常由评估类节点、预警事件或医护判断触发，不应被理解为普通执行节点。

- 退出规则不等同于删除方案或删除患者计划，而是用于定义患者结束当前管理周期、进入下一阶段、转入其他方案或停止管理的业务条件。

## 4. 总结

健康管理方案体系的核心不是“配置一份方案”，而是建立一套可持续运行的服务闭环。

一份成熟的健康管理方案应围绕健康管理主题，标准化组织以下内容：

```text
管理主题
-> 适用对象
-> 基线评估
-> 管理目标
-> 监测数据
-> 管理路径节点
-> 预警干预
-> 阶段评估
```

系统建设上，应坚持：

- 主题标准化。
- 目标可量化。
- 数据可追踪。
- 动作可执行。
- 异常可处理。
- 结果可评估。
- 历史可追溯。

## 5. 行业依据与框架合理性说明

当前健康管理方案内容框架并不是单纯的功能清单，而是围绕慢病和长期健康管理形成的一套服务闭环。

从行业实践看，慢病管理通常不是一次性诊疗行为，而是围绕特定人群持续开展状态识别、目标设定、数据监测、自我管理、干预执行、异常处理和阶段复盘。当前框架能够覆盖这一完整过程。

### 5.1 行业依据

以下行业依据可作为当前内容框架的外部支撑。它们共同指向一个基本判断：健康管理方案应围绕目标人群、基线状态、管理目标、持续监测、患者参与、干预执行、异常处理和阶段复盘形成闭环。

### 5.2 框架合理性判断

基于以上行业实践，当前框架是合理的。它既覆盖了慢病管理的基本服务过程，也适配数字健康产品所需的配置化能力。

它的核心价值在于把健康管理方案拆成边界清晰的模块：

- 管理主题：定义管理场景。
- 适用对象：定义方案适合谁。
- 基线评估：定义患者当前状态。
- 管理目标：定义要达到什么结果。
- 监测数据：定义需要持续关注的数据对象。
- 管理路径节点：定义方案在管理周期内的执行编排。
- 预警干预：定义异常识别和后续处理。
- 阶段评估：定义阶段复盘和下一步判断。

因此，当前框架不应被理解为字段堆砌，而应被理解为一套围绕健康管理主题组织的服务闭环。

### 5.3 后续设计边界

后续产品设计中，需要重点守住以下边界：

- 监测数据是数据对象，不是执行动作。
- 管理路径节点是配置层的统一编排单元，不预先绑定为任务、打卡、处方或宣教等具体业务对象。
- 方案模板中的路径节点不配置固定日期，而应基于管理开始时间配置相对时间规则。
- 重复执行场景应通过一个路径节点配置重复规则，由系统在患者计划实例中展开具体执行安排。
- 预警干预需要同时包含异常识别和后续处理动作。
- 评估类节点用于判断阶段效果和下一步安排，不只是结果展示。

整体来看，当前框架适合作为健康管理方案的标准内容框架，用于指导后续方案模板、患者健康计划实例、管理路径配置、预警干预和阶段评估等能力建设。
